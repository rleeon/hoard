# 1.5.4 — Modo Automático que de verdad sincroniza: diff restore, upload periódico, reactividad UI

> Quinto ciclo. Cierra cuatro grietas que el user reportó después de
> probar 1.5.3:
>
> 1. El toggle "Modo Automático" no sube archivos por sí solo: el
>    scheduler emite `automatic-tick` y el frontend re-escanea + re-trackea,
>    pero no fuerza backup de los saves ya tracked. Si el watcher se
>    perdió un evento, el slot se queda obsoleto.
> 2. UI dice "Copiar" en español donde debería decir "Subir" (save → cloud).
>    El verbo "copiar" es ambiguo (portapapeles vs backup) y no transmite
>    dirección.
> 3. Al pulsar Modo Automático, `set_automatic_mode` persiste `auto_restore
>    = true` en disco y empuja al agent, pero el toggle correspondiente en
>    Settings no se refresca — el store `prefs` de Svelte no se actualiza
>    con el Prefs retornado por el comando. El user ve el cambio en
>    `prefs.json` pero la UI miente.
> 4. `auto_restore` actual solo dispara si el directorio local está vacío
>    o ausente (`is_path_empty_or_missing`). El user quiere reconciliación:
>    si faltan archivos del snapshot remoto en local, traerlos sin
>    sobreescribir lo que ya esté.
>
> Plus: el user pide un documento markdown en el Escritorio que explique
> el flujo completo del Modo Automático, parte por parte, para poder
> apuntar qué está mal después.
>
> Plan único fuente de verdad. Log vivo en
> [`1.5.4-log.md`](1.5.4-log.md).

## §0. Diagnóstico actual (post-1.5.3)

Resumen del recon (ver `1.5.4-log.md` entrada inicial para detalle):

1. `crates/hoard-desktop/src/commands/automatic.rs:55-86` emite
   `automatic-tick` cada N horas. `lib/stores/automatic.ts:143-161`
   escucha y dispara `runAutomaticSetup()` que solo hace
   scan + add_game_to_tracking + boot_agent. **No upload**.
2. `crates/hoard-agent/src/agent.rs:549-587, 719-750`: `auto_restore`
   gated por `is_path_empty_or_missing(&local_path)`. Sin diff.
3. `crates/hoard-desktop/src/commands/prefs.rs:120` `set_automatic_mode`
   retorna Prefs pero no emite evento Tauri. El frontend
   `App.svelte` actualiza solo su `automaticMode` local, no el store
   global `prefs`.
4. `es.json` usa "Copiar" en `dashboard.back_up`. EN/DE/FR/IT/JA/PT/ZH
   ya usan equivalente correcto ("Back up", "Sichern", "Sauvegarder",
   "Backup", "バックアップ", "Salvar", "备份"). Solo ES está confuso.

## §1. Objetivos no-negociables

1. **Modo Automático sube saves obsoletos en cada tick.** El scheduler
   debe disparar también un backup de cada save tracked cuyo contenido
   local difiera del último snapshot remoto. Vía evento `automatic-tick`
   que el frontend procesa como "scan + restore-diff + backup-stale".
2. **Reactividad inmediata del toggle `auto_restore` en Settings.**
   Cuando el user activa Modo Automático, el toggle `auto_restore` se
   pinta como ON en Settings sin reload. Cualquier cambio a Prefs
   desde otro punto (sidebar toggle, comando programado) se refleja
   en Settings al instante.
3. **Auto-restore por diff, no por carpeta-vacía.** `sweep_for_auto_restore`
   y el flow de boot deben descargar archivos del snapshot remoto que
   falten en local, sin sobreescribir los que ya estén. La condición
   "vacío" se vuelve "vacío O snapshot remoto contiene archivos no
   presentes localmente".
4. **Rename `dashboard.back_up` en ES (y revisar otras 7 locales).**
   "Copiar" → "Subir" en español. Otras locales: confirmar que ya usan
   el verbo equivalente. Si alguna usa el cognado equivocado, fijarla.
5. **Doc en `/home/insider/Desktop/hoard-modo-automatico.md`** que
   explique el flujo del Modo Automático parte por parte (toggle →
   persistencia → scheduler → tick → frontend → scan → diff-restore →
   backup-stale → cascada `auto_restore`), con paths y líneas exactas
   y una sección "Qué puedes esperar como user" en lenguaje plano.

## §2. Anti-objetivos

- **No** merge bidireccional ni resolución de conflictos: si local tiene
  archivos que el server no tiene, los deja como están y los sube en el
  próximo backup. Si local tiene un archivo que también está en remoto
  y difieren, **no se toca el local** (el usuario perdería trabajo). El
  diff solo añade.
- **No** cambio de cadencia del watcher (5 s debounce sigue).
- **No** UI nueva — los fixes son comportamiento y rename.
- **No** rotar/eliminar el endpoint o tabla `whoami`. Reuso de datos.

## §3. Visión: cómo se siente después de 1.5.4

1. El user activa Modo Automático ⇒ inmediatamente en Settings el
   toggle "Restauración automática" se pinta verde sin cambiar de
   pestaña.
2. Cada N horas, el modo automático también sube cualquier save cuyo
   contenido en disco haya cambiado desde el último backup
   (catch-up por si el watcher se perdió algo).
3. Si el user borra una carpeta de save por accidente, en el próximo
   tick (o en el boot del agent) los archivos vuelven del snapshot.
   Si la carpeta tiene cosas pero faltan algunos archivos del
   snapshot, los faltantes se descargan; los presentes no se tocan.
4. El botón "Copiar" del Dashboard se llama "Subir" en español.
5. Hay un MD en el escritorio que el user puede leer y anotar qué
   no concuerda con su expectativa.

## §4. Arquitectura objetivo

### §4.1 Reactividad `set_automatic_mode` → store prefs

`set_automatic_mode` ya retorna `Result<Prefs, AppError>`. El frontend
en `App.svelte:toggleAutomatic` actualmente hace:

```ts
await api.setAutomaticMode(next);
automaticMode = next;
```

Cambiar a:

```ts
const updated = await api.setAutomaticMode(next);
prefs.set(updated);
automaticMode = updated.automatic_mode;
```

Importar `prefs` de `lib/stores/prefs.ts`. Como Settings.svelte ya se
suscribe a `$prefs`, el toggle se refresca automáticamente.

(Opcional: emit Tauri event `prefs-changed` desde Rust cuando hay un
cambio que no pasa por el frontend — fuera de scope para 1.5.4 porque
los únicos otros writers son comandos Rust que ya retornan Prefs).

### §4.2 Auto-restore por diff

`crates/hoard-agent/src/agent.rs`:

1. Renombrar `is_path_empty_or_missing` → `local_needs_restore` con
   nueva firma: `async fn local_needs_restore(local_path: &Path,
   remote_snapshot: &SaveSummary) -> bool` o similar.
2. La función retorna `true` si:
   - `local_path` no existe o está vacío (caso original), o
   - El snapshot remoto contiene archivos no presentes localmente.
3. `run_auto_restore` cambia a `run_auto_restore_diff`: descarga el
   tarball remoto en un tempdir, walka el contenido, copia a
   `local_path` solo los archivos que **no existan** en local
   (preservando contenido local). Si un archivo existe local y
   remoto con bytes diferentes, **no se toca** local.
4. Logging detallado: `tracing::info!("auto-restore diff: restoring N
   files (M skipped — already present locally)")`.

Riesgo del comparison "archivo presente local pero distinto":
preservar local. Justificación: el user nunca pierde trabajo. Si
sube algo nuevo, el watcher lo sube. Si quiere forzar restore
completo, hay un botón explícito "Restaurar snapshot" en la UI
(no Modo Automático).

### §4.3 Auto-backup en `automatic-tick`

Frontend `lib/stores/automatic.ts`: tras el flujo de scan + track,
añadir paso "backup-stale":

```ts
const tracked = await api.listTrackedSaves();
for (const save of tracked) {
  try {
    await api.requestBackup(save.id); // Tauri command
  } catch (e) {
    console.warn(`automatic-tick: backup-stale failed for ${save.id}`, e);
  }
}
```

`api.requestBackup` envuelve el comando Tauri `trigger_backup(save_id)`
que ya existe o se añade — auditar `crates/hoard-desktop/src/commands/`
para reutilizar; si no existe, añadir thin wrapper a
`AgentHandle::trigger_backup_for_save(save_id)`.

`AgentHandle` (en `hoard-agent`) ya tiene mecanismo de encolado
para backups manuales. Si lo expone como pub fn lo reutilizamos.

Lock: si un backup ya está en vuelo para ese save, el agent debe
hacer dedupe (probablemente ya lo hace). No reimplementar.

### §4.5 Doc en el Escritorio

`/home/insider/Desktop/hoard-modo-automatico.md`. Estructura:

```markdown
# Modo Automático — cómo funciona, parte por parte

(escrito 2026-05-20, para Hoard v1.5.4)

## El toggle (UI)
- Dónde vive: sidebar inferior izquierda, App.svelte:310-339.
- Estado: persistido en prefs.json como `automatic_mode: bool` y
  `automatic_scan_interval_hours: u32` (default 6).

## Qué pasa cuando lo activas (paso a paso)
1. Click → `toggleAutomatic` en App.svelte.
2. Llama `api.setAutomaticMode(true)` → comando Tauri
   `set_automatic_mode` (crates/hoard-desktop/src/commands/prefs.rs).
3. Persiste `automatic_mode=true` Y `auto_restore=true` en prefs.json.
4. Si el agent está corriendo, empuja la nueva `auto_restore` vía
   `AgentHandle::set_auto_restore`.
5. Arranca el scheduler de fondo (commands/automatic.rs).
6. Retorna el Prefs actualizado al frontend → el store `prefs`
   global se refresca → Settings.svelte ve `auto_restore=true` al
   instante.

## Qué hace el scheduler (cada N horas)
- N = `automatic_scan_interval_hours`, default 6 h.
- Primer tick se consume sin acción (no spam inmediato).
- En cada tick siguiente, emite el evento Tauri `automatic-tick`.

## Qué hace el frontend al recibir `automatic-tick`
1. Detecta juegos nuevos (`scanLibrary`).
2. Trackea los de alta confianza con path encontrado.
3. Para cada save ya tracked, pide al agent que verifique si el
   contenido local difiere del último snapshot, y suba si toca.

## Auto-restore (diff, no destructivo)
- Disparado en boot del agent y en cada tick del modo automático.
- Compara archivos remotos contra locales por nombre relativo.
- Si falta algún archivo local que está en el snapshot remoto,
  lo descarga.
- Si un archivo existe local y remoto pero su contenido difiere,
  NO se toca el local (eso es trabajo nuevo del user).
- Si local tiene archivos extra (no en remoto), los deja y los
  subirá el watcher cuando detecte el cambio.

## Qué pasa cuando lo desactivas
1. `automatic_mode=false` en prefs.json.
2. `auto_restore` queda como estaba (independencia hacia abajo).
3. Scheduler abortado.
4. Watcher sigue corriendo y subiendo cambios — no se ve afectado.

## Botón "Subir" del Dashboard
- Antes (1.5.3): "Copiar" (confuso).
- Ahora: "Subir".

## Lo que NO hace el Modo Automático
- No descarga snapshots remotos si tienes datos locales válidos
  (eso es opt-in vía botón explícito).
- No resuelve conflictos por diff — si tu save local y remoto
  difieren, gana local.
- No descarga saves que no estés trackeando.
```

Sección final: "Qué probar y qué reportar si algo falla".
