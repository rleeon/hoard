# 1.5.1 — Discovery agresivo + "eliminar juego" + saves huérfanas

> Continuación del overhaul de detección. 1.5.0 cerró las seis grietas
> estructurales documentadas en
> [`detection.md`](detection.md) (ADR 0009). 1.5.1 ataca lo que aún
> rompe la experiencia diaria del usuario: juegos que el pipeline no
> encuentra a pesar de tenerlos instalados, y la imposibilidad de
> recuperarse de un mal track sin tocar la base de datos del server a
> mano.
>
> Este plan es la única fuente de verdad de qué se construye en 1.5.1
> y en qué orden. El registro vivo de qué prompt se ha cerrado está en
> [`1.5.1-log.md`](1.5.1-log.md). Si te desvías del plan, actualiza

## §0. Diagnóstico actual (post-1.5.0)

1.5.0 dejó la detección sólida para los casos que el catálogo Ludusavi
cubre. Pero hay tres clases de fallos que siguen golpeando al usuario
en su uso real:

1. **Juegos detectados como "Steam-only" sin save path.** El scan
   sabe que el juego está instalado (Steam library scan funciona),
   pero no encuentra dónde guarda sus saves. Causa raíz: el filesystem
   heuristic actual sólo expande las plantillas del catálogo Ludusavi.
   Si Ludusavi no tiene entrada para el juego, o tiene la entrada pero
   con plantillas que no aplican al layout real (por ejemplo, indies
   que guardan saves dentro de su propio install dir, o juegos que
   usan un subdir custom dentro de `AppData/LocalLow`), el resultado
   es un card amber "No save folder yet" sin información accionable.

2. **Juegos con saves en sitios "raros" no listados por Ludusavi.**
   Indies recientes, mods, juegos GOG-only, juegos comprados fuera de
   Steam. El usuario tiene que recordarse a sí mismo dónde guarda
   cada uno y picarle el path a mano. La app es pasiva.

3. **No hay forma de recuperarse de un mal track.** El botón
   "Desmonitorizar" actual (papelera roja en la strip de "Juegos en
   seguimiento") sólo borra la entrada del `CliState` local — los
   snapshots quedan en el server. Diseño intencional para no perder
   backups por accidente. Pero el efecto secundario es que **un juego
   trackeado con un path incorrecto no puede re-detectarse**: tras
   desmonitorizar, el juego sigue ahí server-side y la próxima vez
   que se re-añade desde Library, vuelve a engancharse al save
   existente (HTTP 409 → swallow → reuse). Para forzar un re-escan
   limpio el usuario tiene que entrar al server y borrar la fila a
   mano.

Bonus: **saves huérfanas en server.** Si el usuario reinstala o cambia
de máquina, las saves quedan server-side pero el `CliState` local
está vacío. La strip de "Juegos en seguimiento" filtra por CliState
local (`list_tracked_saves` línea 353 de
`crates/hoard-desktop/src/commands/library.rs`), así que esas saves
son invisibles en la UI y no hay forma de eliminarlas sin
`hoard-admin`.

## §1. Objetivos no-negociables

1. **Discovery agresivo:** para todo juego de Steam (nativo o vía
   Proton) que el pipeline no haya resuelto a un save path, walkear
   el install dir y el prefix con heurística genérica buscando dirs
   con nombre `save / saves / savegame / save games / save_games /
   slot* / profile*` o archivos `*.sav / *.save / *.profile / *.dat`
   dentro de dirs con nombre game-like. El walker tiene una
   profundidad acotada y un timeout por raíz para no convertirse en
   un find recursivo del filesystem entero.

2. **Fuzzy match contra Ludusavi por nombre.** Cuando un juego de
   Steam no tiene appid en Ludusavi y el slug exacto no coincide,
   intentar match por similitud (Levenshtein normalizado o trigram
   sobre el `display_name` slugificado). Confidence `Low`. Sirve
   sobre todo para juegos cuyo nombre Steam y nombre Ludusavi
   divergen ligeramente (re-ediciones, sufijos "Definitive",
   localización del título).

3. **Botón "Eliminar juego" en la strip de Juegos en seguimiento.**
   Visualmente distinto del botón desmonitorizar (rojo más intenso,
   icono diferente). Click → modal de confirmación con texto explícito
   sobre **qué se borra del server** (snapshots, ficheros, metadata).
   Acción → llama al endpoint `DELETE /v1/saves/{id}` que ya existe
   server-side (`crates/hoard-server/src/routes/saves.rs:377`), limpia
   CliState.saves y CliState.manual_paths, y al siguiente scan el
   juego reaparece como no-tracked listo para re-añadir.

4. **Saves huérfanas siempre visibles.** `list_tracked_saves` deja de
   filtrar por CliState local. Saves del server sin CliState aparecen
   en la strip con flag `orphan: true`; la UI las muestra con un
   subrayado discreto ("Sin estado local") y permite eliminarlas con
   el nuevo botón rojo. El botón papelera (desmonitorizar) en saves
   huérfanas es no-op visualmente disabled — no hay nada local que
   limpiar.

## §2. Anti-objetivos

- **No** tocar el shape del catálogo Ludusavi ni añadir un catálogo
  propio. El ADR 0009 dejó Ludusavi como única fuente de verdad y eso
  se respeta.
- **No** rehacer el filesystem heuristic existente. El walker
  agresivo es complementario: corre **sólo** para slugs que ya
  pasaron por el heuristic principal y siguen sin paths resueltos.
- **No** tocar el flow de añadir un juego. La UX de descubrir y
  añadir no cambia; lo que cambia es qué se descubre.
- **No** introducir un walker que cruce filesystem boundaries
  (montajes, symlinks fuera del prefix). El walker se queda dentro de
  `install_dir` o `prefix_root/drive_c/users/steamuser/` según el
  caso.

## §3. Visión: cómo se siente la app después de 1.5.1

1. El usuario abre Library y escanea. Aparecen detectados juegos
   que en 1.5.0 salían como amber "No save folder yet": indies que
   guardan saves en `<install>/save/`, juegos GOG mal nombrados,
   etc. Con confidence `Low` y un badge naranja que diga "Detección
   heurística — revisa antes de añadir".
2. Cuando elige un juego trackeado de la strip de arriba, ve dos
   botones: papelera (desmonitorizar local, mismo de hoy) y otro rojo
   intenso (eliminar del server). Si el path estaba mal o el juego
   ya no existe, click en eliminar → modal con copy explícito → el
   juego desaparece de tracked y aparece como no-tracked en el grid
   de scan, listo para re-añadir.
3. Si reinstala la máquina o cambia de PC, las saves del server
   aparecen en la strip incluso sin haber re-tracked nada. Puede
   eliminarlas directamente desde la UI o re-añadirlas para que la
   detección se enganche.
4. Diagnostics (panel oculto P-DET-6) sigue funcionando y ahora
   muestra **también** los walks agresivos: qué dirs visitó, qué
   archivos consideró save-like y por qué descartó los que descartó.

## §4. Arquitectura objetivo

### §4.1 Pipeline post-1.5.1

```
catalog Ludusavi  ─┐
steam library      ├─→ cross-ref appid + fuzzy-name
proton prefixes    ─┘                           │
                                                ▼
                                     for each slug:
                                       ▸ expand templates → heurística fs (1.5.0)
                                       ▸ proton expand     (1.5.0)
                                       ▸ refine save-dir   (1.5.0)
                                       ▸ if still no paths:
                                            └─▶ AGGRESSIVE WALKER  ←─ nuevo en 1.5.1
                                       ▸ apply manual_paths (1.5.0)
                                                │
                                                ▼
                                        DetectionReport
```

El walker corre **sólo** para slugs con `found_paths.is_empty()`
tras el refinement actual. Recibe como entrada: el slug, el
`install_dir` de Steam (si lo hay), y el `prefix_root` Proton (si lo
hay). Recorre con `depth ≤ 4` desde cada raíz, ignorando dirs grandes
conocidos (binaries, locales del juego, `bin`, `lib`, `node_modules`,
`.git`, etc.), parando si pasa un timeout fijo (~2s por raíz) o si
encuentra ≥ 5 candidatos válidos.

### §4.2 Walker — heurística

Un dir es "save-like" si su nombre matchea `SAVE_PATTERNS` ya
existente (`save`, `saves`, `savegame`, `savegames`, `save games`,
`save_games`) o si su nombre tiene la forma `slot*`, `profile*`,
`user*` con dígitos. Confianza `Low` si sólo matchea por patrón;
sube a `Medium` si dentro del dir hay archivos `*.sav`, `*.save`,
`*.profile`, `*.json` o `*.dat` modificados en los últimos 90 días.

Un dir es game-like (worth descending into) si su nombre slugificado
matchea el slug del juego, su display name, o un alias conocido del
catálogo Ludusavi.

### §4.3 Fuzzy match Ludusavi

Para cada `SteamApp` que no encuentre entrada Ludusavi por appid:
slugificar el `name` con la misma función `slugify` que usa el
catálogo, y comparar contra todos los slugs Ludusavi con un threshold
Levenshtein normalizado (`distance / max(len_a, len_b) < 0.15`).
Coste: O(N×M) por scan, pero la base es ~20k entradas y los Steam
apps son típicamente < 200; aceptable.

### §4.4 Delete completo

Frontend: nuevo botón rojo en strip de tracked saves, icono
`Trash` (sólido, distinto del `Trash2` con tapa abierta del botón
actual). Modal con copy específico ("Esto borra todos los snapshots
del servidor — la acción no se puede deshacer").

Backend: nuevo comando Tauri `delete_save_completely(save_id)` en
`crates/hoard-desktop/src/commands/library.rs`. Llama a
`client.delete_save(save_id)` (existe en `crates/hoard-agent/src/api.rs:223`),
luego limpia `CliState.saves.remove(save_id)` y
`CliState.manual_paths.remove(game_slug)` si había override.

### §4.5 Saves huérfanas

`list_tracked_saves` actual filtra por `cli_state.saves.get(&s.id)`.
Cambio: hacer el filter opcional vía un nuevo struct `TrackedSave`
que añada `orphan: bool`. Si el save existe server-side pero no en
CliState, se marca `orphan = true` y `local_path = ""`. El front
muestra esa save con un badge tenue y permite eliminar (no
desmonitorizar — disabled).

## §7. Prompts ejecutables

### P-D151-0 — ADR 0010: aggressive discovery + complete-delete

Escribe `docs/decisions/0010-aggressive-discovery-and-delete.md`
siguiendo el formato de ADR 0009 (Status / Context / Decision /
Consequences / Alternatives considered). Status: Accepted. Date:
hoy.

Context cubre las tres clases de fallo del §0 de este plan:
juegos detectados como Steam-only sin paths, juegos no listados por
Ludusavi, e imposibilidad de re-escanear un mal track sin tocar
hoard-admin. Cita el handler server `crates/hoard-server/src/routes/saves.rs:377`
y `list_tracked_saves` en `crates/hoard-desktop/src/commands/library.rs:340`.

Decision lista las cinco piezas: walker agresivo gated por
`found_paths.is_empty()` post-refinement, fuzzy-match Levenshtein
contra Ludusavi (threshold 0.15), comando Tauri `delete_save_completely`
que llama al DELETE del server, UI con dos botones diferenciados,
saves huérfanas visibles con flag `orphan`. Justifica el threshold
0.15 (~ 1 error por cada 7 caracteres, conservador).

Consequences cubre: cobertura aumenta para juegos no listados,
falsos positivos posibles del walker mitigados por confidence Low y
badge visible, delete completo es destructivo pero requiere
confirmación, saves huérfanas dejan de ser invisibles.

Alternatives considered y rechazadas: (a) catálogo propio
hand-curated en lugar de fuzzy match (rechazado por ADR 0009),
(b) walker como default en lugar de gated por `is_empty()` (caro,
ruidoso), (c) soft-delete en el botón nuevo en lugar de hard
(complicación sin caso de uso real — para eso ya está
desmonitorizar).

Sin tocar código. Cargo check no aplica. Marca estado DONE en
1.5.1-log.md.

### P-D151-1 — Aggressive walker

Añade en `crates/hoard-agent/src/detection.rs` (mismo módulo, no
crate nuevo) un walker que se invoca **sólo** para slugs cuyo
`found_paths` quede vacío tras el `refine_save_dir` actual.

Firma sugerida:

```rust
fn aggressive_discover(
    slug: &str,
    display_name: &str,
    install_dir: Option<&Path>,
    prefix_root: Option<&Path>,
    timeout_per_root: Duration,
    max_depth: usize,
) -> Vec<DiscoveredSavePath>
```

Donde `DiscoveredSavePath { path, confidence: Confidence, reason: String }`
para que el Diagnostics panel (P-DET-6) pueda mostrar la razón.

Heurística de match (constantes en el mismo módulo):

- Dir name slug ∈ `{save, saves, savegame, savegames, save games,
  save_games}` ⇒ confidence Low, reason "matches SAVE_PATTERNS".
- Dir name match regex `^(slot|profile|user)[\W_]?\d+$` ⇒ Low.
- Si el dir tiene ≥ 1 archivo modificado los últimos 90 días con
  extensión `.sav .save .profile .json .dat .xml` ⇒ promote a
  Medium, reason "matches pattern + recent save-like files".

Reglas:

- Si `install_dir` no es None, walk desde ahí con depth ≤
  `max_depth`. Skip subdirs cuyo nombre esté en `WALK_SKIP`
  (constante: `bin, lib, locale, locales, languages, audio, video,
  movies, music, fonts, shaders, content, _CommonRedist, vcredist,
  dotnet, node_modules, .git, .vs`).
- Si `prefix_root` no es None, walk desde
  `prefix_root.join("drive_c/users/steamuser")` con la misma
  profundidad y skip-list.
- Timeout: si pasan `timeout_per_root` sin terminar, devolver lo
  encontrado hasta ese punto. Usar `Instant::now()` checked a cada
  10 entries.
- Cap: si encuentra ≥ 5 candidatos en una raíz, parar esa raíz.

Integración en `detect_all`:

Después de aplicar `refine_save_dir` y antes de `apply_manual_overrides`,
para cada `(slug, game)` en `by_slug` con `game.found_paths.is_empty()`:
buscar el `install_dir` correspondiente (mapeo via `steam_app_id` →
`SteamApp.install_dir`) y el `prefix_root` correspondiente (vía
`ProtonPrefix.app_id` si `os == Linux`). Llamar al walker. Si devuelve
candidatos, merge igual que el filesystem heuristic (`merge_fs_hit`)
con `confidence` el máximo de los candidatos.

Defaults: `timeout_per_root = Duration::from_millis(1500)`,
`max_depth = 4`. Exportar ambas constantes pub(crate) para que
P-D151-7 pueda tunearlas en tests.

Tests unitarios (mismo archivo):

- `aggressive_discover_finds_save_dir_in_install` — fixture: tempdir
  con `<install>/data/SaveGames/slot1.sav` reciente. Verifica devuelve
  un path con confidence Medium.
- `aggressive_discover_respects_skip_list` — fixture: `<install>/bin/save/`
  no debería aparecer porque `bin` está en `WALK_SKIP`.
- `aggressive_discover_promotes_with_recent_savefile` — fixture: dir
  `<install>/save/` vacío vs dir `<install>/save/` con `slot.sav`
  modificado hoy. Sólo el segundo sube a Medium.
- `aggressive_discover_returns_empty_on_missing_dirs` — `install_dir`
  y `prefix_root` None ⇒ vec vacío sin panic.

Verificar `cargo check --workspace` y `cargo test -p hoard-agent`.
Actualizar 1.5.1-log.md.

### P-D151-2 — Fuzzy match Ludusavi por nombre

En `crates/hoard-manifest/src/ludusavi.rs` o en su lib root, añadir
una función pública:

```rust
pub fn find_by_fuzzy_name(name: &str, threshold: f32) -> Option<&LudusaviEntry>
```

Implementación: slugify `name` igual que el resto del módulo. Iterar
sobre todas las entries del catálogo, calcular Levenshtein
normalizado contra cada slug, devolver la entry con menor distancia
si la distancia es `< threshold`. Si hay empate, prefiere la entry
con `steam_app_id.is_some()`.

Levenshtein: añade `strsim = "0.11"` como workspace dep si no lo
está. Usar `strsim::levenshtein` y normalizar `distance / max(len_a, len_b)`.

Integración en `detect_all`: en la fase de cross-reference Steam →
catálogo, cuando `find_by_steam_app_id` devuelve None **y**
`find_by_slug(slugify(&steam_app.name))` también devuelve None,
intentar `find_by_fuzzy_name(&steam_app.name, 0.15)`. Si matchea,
crear el `DetectedGame` con `confidence = Confidence::Low` y
`reason` registrando que vino del fuzzy match (para el Diagnostics).

Tests unitarios:

- `fuzzy_matches_minor_typo` — buscar "stardew vally" matchea
  "stardew valley".
- `fuzzy_rejects_distant_names` — "destiny" no matchea "civilization".
- `fuzzy_prefers_steam_id` — si dos entries empatan en distancia,
  gana la que tiene `steam_app_id`.
- `fuzzy_returns_none_below_threshold` — exact distance > threshold ⇒
  None.

Verificar `cargo check --workspace` y `cargo test`. 1.5.1-log.md.

## §8. Riesgos y mitigaciones

- **Walker hace falsos positivos.** Mitigación: confidence Low por
  defecto, badge naranja visible "Detección heurística". Diagnostics
  panel muestra la razón.
- **Walker lento en discos lentos.** Mitigación: timeout por raíz
  + cap de 5 candidatos. En SSD modernos un walk depth=4 de un
  install dir típico es < 200ms.
- **Fuzzy match cruza títulos parecidos.** "Civilization V" vs
  "Civilization VI": Levenshtein normalizado = 1/14 ≈ 0.07, sale
  bajo del threshold 0.15. Mitigación: threshold conservador, y el
  cross-reference Steam-→Ludusavi por slug exacto siempre tiene
  prioridad sobre el fuzzy (el fuzzy es fallback).
- **Delete completo es destructivo.** Mitigación: modal de
  confirmación con texto explícito, botón rojo intenso, copy menciona
  "no se puede deshacer".
- **Saves huérfanas confunden al usuario.** Mitigación: badge claro
  "Sin estado local", botón papelera deshabilitado, sólo el nuevo
  botón rojo es accionable.
