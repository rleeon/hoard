# 1.5.2 — Detección Windows seria + Lutris/Bottles

> Tercer ciclo de detección, foco principal Windows. Cierra los huecos
> que 1.5.0 y 1.5.1 dejaron del lado del SO mayoritario: launchers
> no-Steam invisibles, paths en registry descartados silenciosamente,
> "Saved Games" no soportado como token, OneDrive redirigiendo
> Documents sin que la app se entere. Linux recibe paridad con
> Proton añadiendo Lutris y Bottles.
>
> Este plan es la única fuente de verdad de qué se construye en 1.5.2
> y en qué orden. El registro vivo está en
> [`1.5.2-log.md`](1.5.2-log.md). Si te desvías, actualiza este
> archivo primero.

---

## §0. Diagnóstico actual (post-1.5.1)

El recon previo a este plan confirmó cinco grietas que penalizan
sobre todo a usuarios Windows:

1. **Sin detección de launchers no-Steam.** El `crates/hoard-agent/src/steam.rs`
   es la única fuente de "qué juegos hay instalados". Juegos
   comprados en Epic, GOG Galaxy, EA Play, Ubisoft Connect, Battle.net
   o Microsoft Store / Xbox Game Pass son invisibles para Hoard a
   menos que el filesystem heuristic los pille de casualidad. El
   comentario en `crates/hoard-agent/src/detection.rs:16` dice
   "Catches GOG, Epic, DRM-free" pero es aspiracional.

2. **Registry paths descartados silenciosamente.** El catálogo Ludusavi
   tiene un campo `registry:` separado de `files:` con cientos de
   entries del tipo `HKEY_CURRENT_USER/Software/.../SaveLocation`. El
   parser actual (`crates/hoard-manifest/src/ludusavi.rs`) sólo
   deserializa `files`, `steam`, `alias`. Toda la información del
   registry se pierde antes de llegar al pathexpand, así que juegos
   tipo Bethesda Skyrim o Paradox antiguos que guardan paths de save
   en el registro no se resuelven.

3. **`<winSavedGames>` no existe como token.** Windows Vista+ tiene una
   carpeta oficial `%USERPROFILE%\Saved Games` que muchos juegos
   modernos usan. Ludusavi catálogo lo expresa con paths literales
   en algunas entries, pero como nadie expande `<winSavedGames>`, los
   juegos que sí usan ese token quedan sin resolver. Más relevante
   en 1.6.0 si se actualiza el shape del catálogo, pero ya conviene
   tener el token mapeado.

4. **OneDrive redirige Known Folders y nadie lo sabe.** En Windows
   moderno la carpeta Documents puede estar redirigida a
   `C:\Users\<user>\OneDrive\Documents` vía
   `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders`.
   `pathexpand.rs` usa `env::var("USERPROFILE")` y construye paths
   directos sin consultar Shell Folders, así que entradas Ludusavi
   con `<winDocuments>/<game>` apuntan a un Documents inexistente o
   sincronizado donde el juego no escribe.

5. **Linux: Lutris y Bottles invisibles.** 1.5.0 cubrió Proton. Los
   usuarios que juegan vía Lutris (prefixes en
   `~/.local/share/lutris/runners/wine/.../prefixes/<id>/`) o
   Bottles (`~/.var/app/com.usebottles.bottles/data/bottles/bottles/<name>/`)
   no son detectados. Mismo patrón que Proton, distinto layout.

## §1. Objetivos no-negociables

1. **Detectar juegos de Epic Games, GOG Galaxy y Microsoft Store /
   Xbox Game Pass.** Mismo flujo que Steam: parser que devuelve
   `Vec<LauncherApp { app_id, name, install_dir }>` por launcher y se
   integra en `detect_all` igual que `list_installed_steam_games`.

2. **Expand de registry paths del catálogo Ludusavi.** El deserializer
   captura el campo `registry`. En Windows, una nueva función
   `expand_registry_path(template, hive)` lee el valor del registro
   y lo trata como path candidato. En no-Windows devuelve vec vacío.

3. **Soporte de `<winSavedGames>` y OneDrive-aware Known Folders.**
   pathexpand consulta los Shell Folders del registro en Windows para
   resolver Documents/AppData/etc al destino real (con o sin
   redirección OneDrive). En no-Windows el comportamiento actual
   sigue.

4. **Detección de Lutris y Bottles en Linux.** Mismo shape que
   `list_proton_prefixes`: una función por launcher que devuelve
   `Vec<WinePrefix { kind, app_id, prefix_root }>` y se integra en el
   bloque proton expand actual.

5. **Walker agresivo cubre todos los launchers.** El walker añadido
   en 1.5.1 (`aggressive_discover`) corre hoy sólo si Steam library
   scan trajo el install_dir. Tiene que correr también contra
   install_dirs de Epic/GOG/MS y contra prefix_roots de Lutris/Bottles.

## §2. Anti-objetivos

- **No** parsear el manifest YAML hand-curated de Ludusavi vivo (el
  consumido del repo upstream). Mantén el catálogo embebido como
  hoy.
- **No** añadir un sistema de credenciales o login a launchers
  (Epic, GOG, Microsoft). Sólo lectura local de manifests/sqlite/registry.
- **No** modificar el shape del struct `DetectedGame` ni la API
  externa de `detect_all`. Sólo se enriquecen los inputs.
- **No** cubrir EA Play, Ubisoft Connect ni Battle.net en este
  ciclo. Quedan pendientes para 1.5.3 o 1.6.x si la demanda lo
  justifica. (Justificación: parsers de manifests propietarios sin
  estructura estable, ROI bajo vs los Big-3.)

## §3. Visión: cómo se siente la app después de 1.5.2

1. Un usuario Windows que ha comprado juegos en Epic, GOG o Xbox
   Game Pass abre Library y escanea. Aparecen detectados igual que
   los de Steam, con sus saves resueltos contra el catálogo Ludusavi
   o el walker.
2. Juegos cuyos saves Ludusavi documenta en el registro (Skyrim
   classic, algunos Paradox viejos) ya no salen como "Steam-only sin
   path". El path real aparece resuelto vía registry expand y se
   puede trackear normal.
3. Un usuario Windows con OneDrive activo no ve más rutas raras o
   inexistentes — `<winDocuments>` apunta al destino real.
4. Un usuario Linux que juega vía Lutris o Bottles ve sus juegos
   con el save path resuelto contra el prefix correcto, igual que
   ya pasa con Proton.
5. Diagnostics panel (5-click en versión) sigue mostrando paso a
   paso de cada slug: ahora con un signal extra "launcher: epic" /
   "launcher: gog" / "launcher: microsoft" / "registry: HKCU/..."
   visible.

### §4.2 Launchers no-Steam

Tres parsers nuevos en un módulo `crates/hoard-agent/src/launchers.rs`:

- **Epic Games**: `pub fn list_installed_epic_games(os: Os) -> Vec<EpicApp>`.
  En Windows lee `%PROGRAMDATA%\Epic\EpicGamesLauncher\Data\Manifests\*.item`
  (JSON files con campos `InstallLocation`, `DisplayName`, `LaunchExecutable`,
  `CatalogItemId`, `MainGameAppName`). En no-Windows devuelve vec
  vacío.
- **GOG Galaxy**: `pub fn list_installed_gog_games(os: Os) -> Vec<GogApp>`.
  En Windows lee el sqlite `%LOCALAPPDATA%\GOG.com\Galaxy\storage\galaxy-2.0.db`
  (tabla `InstalledExternalProducts` o equivalente — el parser
  intenta varias tablas conocidas, robusto a cambios menores de
  schema). Devuelve `GogApp { product_id, name, install_dir }`.
- **Microsoft Store**: `pub fn list_installed_msstore_games(os: Os) -> Vec<MsApp>`.
  En Windows lee el registro
  `HKCU\Software\Microsoft\GamingServices\PackageRepository\Package`
  enumerando subkeys. Para cada package, busca el install dir y
  comprueba si es un juego (`Properties\Category` o presencia de
  ejecutables conocidos). Saves típicamente en
  `%LOCALAPPDATA%\Packages\<package_id>\SystemAppData\wgs\`.

Los tres struct tienen el campo común `install_dir: PathBuf`. La
integración en `detect_all` los suma al lookup que hoy es sólo
Steam: la cross-reference contra Ludusavi sigue siendo por slug
exacto / fuzzy match.

### §4.3 Registry expand

Schema Ludusavi actualizado (P-D152-1):

```rust
pub struct LudusaviEntry {
    pub slug: String,
    pub steam_app_id: Option<u32>,
    pub paths: Paths,        // existente
    pub registry: Vec<RegistryPath>, // nuevo
}

pub struct RegistryPath {
    pub key: String,   // "HKEY_CURRENT_USER/Software/..."
    pub value: Option<String>,  // valor concreto si Ludusavi lo especifica, else None
}
```

Expand (P-D152-2), Windows-only via `winreg` crate (workspace dep
nueva, cfg(windows)):

```rust
#[cfg(windows)]
pub fn expand_registry_path(reg: &RegistryPath) -> Vec<PathBuf>;

#[cfg(not(windows))]
pub fn expand_registry_path(_reg: &RegistryPath) -> Vec<PathBuf> {
    Vec::new()
}
```

La función abre el hive (`HKEY_CURRENT_USER` o `HKEY_LOCAL_MACHINE`),
recorre la subkey, lee el value (default value si `value` es None),
y devuelve el path si el valor es válido. Si el path es un literal
absoluto, se devuelve tal cual. Si contiene placeholders Ludusavi,
se expanden recursivamente con la lógica de pathexpand existente.

### §4.4 Saved Games + Known Folders

Token nuevo `<winSavedGames>` en pathexpand, mapeado a:

- Windows: usar `SHGetKnownFolderPath` vía `windows` crate o
  fallback a `%USERPROFILE%\Saved Games`.
- No-Windows: `Vec::new()`.

OneDrive awareness: para `<winDocuments>`, `<winAppData>`,
`<winLocalAppData>` etc., en Windows leer
`HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders`
para obtener el path real (puede estar redirigido a OneDrive). Si
el registro no tiene la key, fallback al path actual basado en
env vars. La función helper resuelve estos paths una vez al inicio
del scan y cachea en una struct `WindowsKnownFolders` que se pasa
a `expand_path`.

### §4.5 Lutris + Bottles prefixes

Módulo nuevo o extensión de `crates/hoard-agent/src/steam.rs` (mejor
módulo separado `crates/hoard-agent/src/wine_prefixes.rs`):

```rust
pub struct WinePrefix {
    pub kind: PrefixKind,  // Proton | Lutris | Bottles
    pub app_id: Option<String>,  // appid para Proton, game name slug para Lutris/Bottles
    pub prefix_root: PathBuf,
}

pub fn list_wine_prefixes(os: Os) -> Vec<WinePrefix>;
```

Esta función absorbe `list_proton_prefixes` existente (mantener el
shape compat con un wrapper deprecated) y suma:

- **Lutris**: walk de `~/.local/share/lutris/runners/wine/.../prefixes/`.
  El nombre del prefix suele ser el slug del juego o un id Lutris;
  cross-reference best-effort contra Ludusavi por nombre.
- **Bottles**: walk de `~/.var/app/com.usebottles.bottles/data/bottles/bottles/`
  (o el path nativo si no es flatpak).

En no-Linux devuelve sólo Proton (cuando aplique) o vacío.

### §4.6 Aggressive walker — input expandido

Hoy el walker corre sólo con el `install_dir` de Steam y el
`prefix_root` de Proton. Nuevo en P-D152-5: construir el mapa
`appid → install_dir` con los install_dirs de Epic, GOG y MS también
(con appid sintético si no tienen Steam appid), y el mapa
`appid → prefix_root` con Lutris y Bottles. El walker no cambia.

### P-D152-0 — ADR 0011

Redacta `docs/decisions/0011-windows-detection-and-extra-prefixes.md`
siguiendo el formato del ADR 0010 (Status / Context / Decision /
Consequences / Alternatives considered). Status: Accepted, date 2026-05-19.

Context cubre las cinco grietas del §0: launchers no-Steam invisibles,
registry paths descartados, Saved Games sin token, OneDrive
ignorado, Lutris/Bottles invisibles. Cita
`crates/hoard-agent/src/steam.rs`, `crates/hoard-manifest/src/ludusavi.rs`,
`crates/hoard-agent/src/pathexpand.rs`.

Decision lista las seis piezas: parsers Epic/GOG/MS unificados en
`launchers.rs`, schema Ludusavi extendido con `registry: Vec<RegistryPath>`,
`expand_registry_path` Windows-only vía `winreg` crate, token
`<winSavedGames>` y Known Folders OneDrive-aware vía
`SHGetKnownFolderPath` + registry Shell Folders, módulo
`wine_prefixes.rs` que absorbe Proton y suma Lutris/Bottles,
aggressive walker recibe los install_dirs/prefix_roots nuevos.

Consequences: cobertura sube drásticamente en Windows (Big-3
launchers + registry-based saves), cobertura Linux mejora con
Lutris/Bottles, deps nuevas (`winreg`, `windows` o equivalente,
`rusqlite` para GOG), el código Windows-specific se aísla detrás
de cfg-gates con stubs no-op cross-platform.

Alternatives considered y rechazadas: (a) cubrir EA Play / Ubisoft
Connect / Battle.net en este ciclo (manifests opacos, ROI bajo), (b)
shellear powershell `Get-AppxPackage` en lugar de leer el registro
para Microsoft Store (lento, frágil), (c) reescribir el catálogo
embebido para incluir el registry inline en vez de campo separado
(rompe compat con upstream Ludusavi).

Sin código. Marca P-D152-0 DONE en `1.5.2-log.md`.

### P-D152-1 — Ludusavi schema: capturar `registry`

En `crates/hoard-manifest/src/ludusavi.rs`:

1. Añadir struct público `RegistryPath { pub key: String, pub value: Option<String> }`.
2. Extender el struct `LudusaviEntry` con `pub registry: Vec<RegistryPath>` (default vacío con `#[serde(default)]`).
3. Extender el deserializer/parser para que lea el campo `registry` del JSON embebido. El JSON Ludusavi tiene la forma:

   ```json
   "GameSlug": {
       "files": { ... },
       "registry": {
           "HKEY_CURRENT_USER/Software/Foo/Bar": {
               "when": [...],
               "tags": ["save"]
           }
       },
       "steam": { "id": 12345 }
   }
   ```

   Convierte cada key del map `registry` en un `RegistryPath { key: <la key>, value: None }` (el value field queda None — Ludusavi por defecto lee el value default de la subkey).

4. Actualiza la inicialización del catálogo embebido para que el campo esté presente. La función `catalog()` debería devolver entries con `registry` populado donde corresponda.

5. Si `find_by_slug`, `find_by_steam_app_id`, `find_by_fuzzy_name` ya existen (sí lo hacen post-1.5.1), no cambies sus firmas — sólo asegúrate de que el campo nuevo se serializa.

Tests unitarios:

- `parses_registry_field_from_entry` — fixture JSON con entry que tiene `registry` y verifica que `LudusaviEntry.registry` contiene la key esperada.
- `entry_without_registry_defaults_to_empty` — entry sin campo `registry` ⇒ `Vec::new()`.

Verificar `cargo check --workspace` y `cargo test -p hoard-manifest`.
Marca P-D152-1 DONE en `1.5.2-log.md`.

### P-D152-2 — pathexpand Windows: registry + Saved Games + OneDrive-aware

En `crates/hoard-agent/src/pathexpand.rs`:

1. Añadir dep workspace `winreg = "0.52"` (o version compatible con
   2026 ecosystem) con `cfg(windows)` en `crates/hoard-agent/Cargo.toml`:

   ```toml
   [target.'cfg(windows)'.dependencies]
   winreg = "0.52"
   ```

   También añadir `windows-sys = { version = "0.59", features = ["Win32_UI_Shell", "Win32_System_Com"] }` para `SHGetKnownFolderPath` (sólo si no añade ruido a Cargo.lock; alternativa: hardcodear `%USERPROFILE%\Saved Games` y leer User Shell Folders del registry para los demás).

2. Token nuevo `<winSavedGames>` en el match de `expand_placeholder`. En Windows resolverlo a `%USERPROFILE%\Saved Games` (preferir
   `SHGetKnownFolderPath(FOLDERID_SavedGames)` si añades windows-sys, sino fallback hardcoded). En no-Windows devuelve `Vec::new()`.

3. Función nueva pública (sólo Windows):

   ```rust
   #[cfg(windows)]
   pub fn expand_registry_path(reg: &RegistryPath) -> Vec<PathBuf>
   ```

   Parsea `reg.key` separando hive ("HKEY_CURRENT_USER" / "HKEY_LOCAL_MACHINE") y subkey. Abre con `winreg::RegKey::predef`. Lee `reg.value` (default value si None) como string. Si la key no existe o el value no es legible, devuelve `Vec::new()`.

   Versión cross-platform:

   ```rust
   #[cfg(not(windows))]
   pub fn expand_registry_path(_reg: &RegistryPath) -> Vec<PathBuf> { Vec::new() }
   ```

4. OneDrive-aware Known Folders. En Windows, antes de resolver `<winDocuments>`, `<winAppData>`, `<winLocalAppData>`, `<winLocalAppDataLow>`, `<winPublic>`, `<winProgramData>` por env var, consulta primero
   `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders`
   (valores: `Personal` → Documents, `AppData` → Roaming, `Local AppData` → Local, etc.). Si el value existe, expand `%USERPROFILE%` o similares y úsalo. Si no, fallback a env. Toda esta lógica vive detrás de un helper `windows_known_folder(token: &str) -> Option<PathBuf>` con `#[cfg(windows)]`. En no-Windows el match actual sigue intacto.

5. Documenta cada placeholder nuevo con docstrings cortos en el mismo
   archivo (1-2 líneas).

Tests:

- `expands_winsavedgames_token` (cfg-gated o usando fixture HOME isolation).
- `expand_registry_returns_empty_when_key_missing` (cfg(not(windows)) sólo verifica el no-op).
- En Windows: marcar con `#[ignore]` si depende del registry real de la máquina.

Verificar `cargo check --workspace` (también `cargo check --target x86_64-pc-windows-gnu` si está disponible — opcional, no bloquea).

### P-D152-3 — Launchers no-Steam (Epic + GOG + Microsoft Store)

Crea `crates/hoard-agent/src/launchers.rs` y declara el módulo en `lib.rs`.

Tres funciones públicas:

```rust
pub fn list_installed_epic_games(os: Os) -> Vec<LauncherApp>;
pub fn list_installed_gog_games(os: Os) -> Vec<LauncherApp>;
pub fn list_installed_msstore_games(os: Os) -> Vec<LauncherApp>;
```

Con `pub struct LauncherApp { pub launcher: LauncherKind, pub app_id: String, pub name: String, pub install_dir: PathBuf }`.

`enum LauncherKind { Epic, Gog, MicrosoftStore }`.

**Epic**: en Windows lee `%PROGRAMDATA%\Epic\EpicGamesLauncher\Data\Manifests\*.item` (JSON files). Parsea con `serde_json::from_str`. Campos relevantes: `InstallLocation`, `DisplayName`, `CatalogItemId`, `MainGameAppName`. Construye `LauncherApp { launcher: Epic, app_id: CatalogItemId, name: DisplayName, install_dir: InstallLocation }`. Skip si `InstallLocation` no existe o no es dir.

**GOG**: en Windows abre el sqlite `%LOCALAPPDATA%\GOG.com\Galaxy\storage\galaxy-2.0.db` con `rusqlite` (workspace dep, prob ya está; sino, añadir `rusqlite = { version = "0.32", features = ["bundled"] }`). Query la tabla `Builds` o `InstalledExternalProducts` — schema cambia entre versiones de Galaxy, así que prueba primero `SELECT productId, productName, installationPath FROM ...` con varias tablas conocidas. Si el sqlite no se puede abrir, devuelve vec vacío (no panic).

**Microsoft Store**: en Windows lee `HKCU\Software\Microsoft\GamingServices\PackageRepository\Package` enumerando subkeys. Para cada subkey lee el value `Root` (path al install dir). Filtra los que tengan al menos un ejecutable o un manifest `appxmanifest.xml`. `app_id` = nombre de la subkey (package family name).

En no-Windows las tres funciones devuelven `Vec::new()`.

Tests:

- `epic_returns_empty_on_no_manifests` — TEMP HOME sin la carpeta Epic.
- `gog_returns_empty_when_sqlite_absent`.
- `msstore_returns_empty_on_non_windows`.
- En Windows con fixtures sintéticos: tests `#[ignore]` con docstring que explica cómo prepararlos.

### P-D152-4 — Lutris + Bottles prefixes

Crea `crates/hoard-agent/src/wine_prefixes.rs` y declara el módulo
en `lib.rs`. Mantén `steam::list_proton_prefixes` existente (no
borrar, está testeado y referenciado); el módulo nuevo lo
**llama** y suma Lutris + Bottles.

API:

```rust
pub enum PrefixKind { Proton, Lutris, Bottles }

pub struct WinePrefix {
    pub kind: PrefixKind,
    pub identifier: String,  // appid para Proton, nombre slug para Lutris/Bottles
    pub prefix_root: PathBuf,
}

pub fn list_wine_prefixes(os: Os) -> Vec<WinePrefix>;
```

**Proton**: wrapper sobre `steam::list_proton_prefixes(os)` mapeando `ProtonPrefix { app_id, prefix_root }` a `WinePrefix { kind: Proton, identifier: app_id, prefix_root }`.

**Lutris**: en Linux, walk de `~/.local/share/lutris/runners/wine/`. Para cada subdir version (`lutris-fshack-7.2-x86_64`, etc.) entra a `prefixes/`. Cada subdir aquí es un prefix con su `drive_c/`. `identifier` = nombre del dir prefix (suele ser un slug del juego). En no-Linux devuelve vec vacío para Lutris.

**Bottles**: en Linux, walk de
`~/.local/share/bottles/bottles/` (nativo) y
`~/.var/app/com.usebottles.bottles/data/bottles/bottles/` (flatpak).
Para cada subdir, el `prefix_root` es el dir mismo (Bottles guarda
`drive_c/` directamente). `identifier` = nombre del bottle. En no-Linux
vec vacío para Bottles.

Tests:

- `list_wine_prefixes_includes_proton` — fixture HOME con `steamapps/compatdata/...`.
- `list_wine_prefixes_includes_lutris` — fixture HOME con layout Lutris sintético.
- `list_wine_prefixes_includes_bottles` — fixture HOME con layout Bottles sintético.
- `list_wine_prefixes_empty_on_windows` — `Os::Windows` ⇒ vec vacío.

Verifica `cargo test -p hoard-agent --test ...` o tests inline.

## §8. Riesgos

- **Crates Windows-specific aumentan superficie de build.** Mitigación:
  `winreg`, `windows-sys`, `rusqlite` van todos bajo cfg(windows) o
  features minimales. Verifica con `cargo check --target x86_64-pc-windows-msvc`
  si está disponible.
- **GOG Galaxy sqlite schema cambia.** Mitigación: el parser prueba
  varias tablas conocidas y devuelve vec vacío si nada matchea —
  no panic.
- **OneDrive registry redirect puede apuntar a folder no existente.**
  Mitigación: stat() el path antes de usarlo; si no existe, fallback
  al env var.
- **`winreg` o `rusqlite` añaden tiempo de compilación.** Mitigación:
  rusqlite con feature `bundled` evita system sqlite pero compila
  C; sopesar bundled-sqlcipher si más adelante hace falta. winreg
  es liviano.
