### P-D151-0 — ADR 0010: aggressive discovery + complete-delete
Fecha: 2026-05-18  ·  Ejecutor: Opus  ·  Estado: DONE

Cambios:
- Redactado el ADR 0010 siguiendo el formato del 0009 (Status / Context /
  Decision / Consequences / Alternatives considered).
- Status: Accepted, 2026-05-18. Extiende el 0009 sin reemplazarlo.
- Context cubre las tres clases de fallo del §0 del plan (Steam sin
  paths, juegos no listados por Ludusavi, imposibilidad de re-escanear
  un mal track) más la cuarta de saves huérfanas server-side. Cita
  `crates/hoard-server/src/routes/saves.rs:377` y
  `crates/hoard-desktop/src/commands/library.rs:340`.
- Decision lista las cinco piezas: walker agresivo gated por
  `found_paths.is_empty()` (depth 4, denylist, timeout 1.5s, cap 5,
  promoción `Low → Medium` por archivos save-like recientes),
  fuzzy-match Levenshtein contra Ludusavi (threshold 0.15, ties prefieren
  `steam_app_id`), comando Tauri `delete_save_completely`, UI con dos
  botones diferenciados (`Trash2` vs `Trash` sólido en `rose-500`),
  saves huérfanas con flag `orphan` en `TrackedSave`.
- Justifica el threshold 0.15 con el caso "Civilization V vs VI"
  (≈ 0.07 — el slug exacto siempre gana primero, fuzzy es fallback).
- Consequences: cobertura sube para slugs no catalogados, falsos
  positivos del walker mitigados por confidence Low + badge "Detección
  heurística", coste O(N×M) del fuzzy acotado a un Library scan,
  delete destructivo mitigado por modal de confirmación con copy
  explícito, orphan visibility cierra la clase "save invisible".
- Alternatives rechazadas: (a) catálogo TOML hand-curated paralelo
  (rechazado por ADR 0009), (b) walker como default sin gating
  (caro + ruidoso), (c) soft-delete (no resuelve el 409 de
  `add_game_to_tracking`), (d) un único botón "smart"
  (conflación semántica peligrosa), (e) threshold < 0.15 (cae el
  caso "Definitive Edition") o > 0.15 (cruza franquicias).

### P-D151-1 — Aggressive walker
Fecha: 2026-05-18  ·  Ejecutor: Opus  ·  Estado: DONE

Cambios:
- Añadido `pub fn aggressive_discover(slug, display_name, install_dir,
  prefix_root, timeout_per_root, max_depth) -> Vec<DiscoveredSavePath>`
  en `crates/hoard-agent/src/detection.rs`. La firma respeta el prompt.
- Tipo público nuevo `DiscoveredSavePath { path, confidence, reason }`
  para que el panel de diagnósticos (P-DET-6) pueda mostrar la razón
  por la que un dir fue aceptado.
- Constantes `pub(crate)` en el mismo módulo: `AGGRESSIVE_WALK_TIMEOUT`
  (1500 ms), `AGGRESSIVE_WALK_MAX_DEPTH` (4),
  `AGGRESSIVE_WALK_MAX_CANDIDATES` (5), `WALK_SKIP` (denylist:
  `bin, lib, libs, locale, locales, languages, audio, video, movies,
  music, fonts, shaders, content, _commonredist, vcredist, dotnet,
  node_modules, .git, .vs`), `SAVE_FILE_EXTENSIONS`
  (`sav save profile json dat xml`), `RECENT_SAVE_FILE_WINDOW`
  (90 días).
- Walker implementado con `std::fs::read_dir` (no `walkdir` — la base
  no lo usa hoy, sin justificación para añadir dep). BFS con stack
  `(path, depth)`, check de timeout cada 10 entries vía
  `Instant::now()`, bail-out por root al alcanzar el cap de 5
  candidatos. Helper `classify_dir_as_save_like` aplica las dos reglas
  de match (`SAVE_PATTERNS` y `slot|profile|user [sep] <digits>`) y
  promueve a `Medium` cuando hay archivos con extensión save-like
  modificados dentro del window. `name_matches_slot_profile_user`
  reconoce el patrón sin pulling regex.
- Integración en `detect_all` (líneas ~355-410, tras el promote de
  `Both → High` y antes de `apply_manual_overrides`): se construye un
  `HashMap<u64, PathBuf>` con los `ProtonPrefix` en Linux, se itera
  sobre las entries con `found_paths.is_empty()`, se llama al walker
  con `install_dir` (de la cross-reference Steam) y `prefix_root`
  (lookup por `steam_app_id`). Los resultados se mergean vía
  `merge_fs_hit`; tras el merge se fija la `confidence` al máximo de
  las del walker (porque `merge_fs_hit` promovería a `Both/High` con
  una entrada Steam previa, lo que sobreestimaría la fuerza de la
  señal — el walker es heurístico, no catálogo). Helper privado
  `confidence_rank` para el max-by-key.
- Walker es no-op cuando `install_dir == None && prefix_root == None`,
  cuando ambos paths no existen, o cuando el slug tiene
  `found_paths` no vacío: cero coste en el happy path.

Archivos tocados:
- `crates/hoard-agent/src/detection.rs` — walker + constantes +
  integración en `detect_all` + 4 tests unitarios. Imports nuevos:
  `std::path::Path`, `std::time::{Duration, Instant, SystemTime}`.

Tests añadidos:
- `detection::tests::aggressive_discover_finds_save_dir_in_install` —
  fixture con `<install>/data/SaveGames/slot1.sav` reciente. Verifica
  que el walker devuelve un hit con `Confidence::Medium` y reason
  que contiene "recent save-like files".
- `detection::tests::aggressive_discover_respects_skip_list` — fixture
  con `<install>/bin/save/`. Verifica que `bin` denylist tapa la
  detección y el resultado es vec vacío.
- `detection::tests::aggressive_discover_promotes_with_recent_savefile`
  — fixtures gemelos: `<install>/save/` vacío vs `<install>/save/`
  con `slot.sav` recién creado. Sólo el segundo sube a `Medium`; el
  primero queda `Low`.
- `detection::tests::aggressive_discover_returns_empty_on_missing_dirs`
  — `(None, None)` y luego `(/definitely/not/a/real/path, ...)`. Ambos
  casos devuelven vec vacío sin panic.

Notas / decisiones de ejecución:
- **Sin `walkdir`** — el plan explícitamente lo desaconseja, la
  recon confirmó que la base no lo usa y `std::fs::read_dir` cubre
  la heurística con la profundidad acotada.
- **Let-chain refactor** — la primera versión usaba
  `if let Ok(age) = X && age <= Y` pero el crate está en edición
  2021 (let-chains son 2024+). Refactor a `if let { if cond }`
  anidado, semánticamente equivalente.
- **Confidence post-merge** — `merge_fs_hit` siempre promueve a
  `Both/High` cuando ya hay un row Steam, lo que es correcto para
  hits del filesystem-heuristic catálogo-driven (dos señales
  independientes) pero exagerado para el walker (sólo una señal
  heurística por nombre). Se sobreescribe el `confidence` tras el
  merge al máximo grado real del walker (`Low` o `Medium`). El
  `source` queda como `Both`/`FilesystemHeuristic` según el merge
  natural; el badge de UI "Detección heurística" puede leer el
  reason de los `DiscoveredSavePath` cuando se cablee en P-DET-6.
- **`display_name` reservado** — la firma incluye `display_name`
  como parámetro aunque la heurística 1.5.1 no la usa todavía
  (la idea era descender sólo en dirs "game-like" cuyo nombre
  slugificado matchee el slug/aliases). Se deja en la signature
  para no romper la API cuando se implemente. Prefijo `_` para
  silenciar el warning.
- **Cap por raíz** — el cap de 5 candidatos se aplica por raíz
  (install_dir y prefix_root cuentan separado), pero el `seen`
  set se comparte entre ambas raíces para evitar duplicados si
  un mismo path apareciera en las dos (no debería, pero defensivo).
- `cargo check --workspace` y `cargo test -p hoard-agent` ambos
  limpios. 51 unit tests + 7 integration tests pasan, sin warnings.
- No se tocó `Library.svelte`, ni `delete_save_completely` (sub-agent
  paralelo, P-D151-3), ni versión, ni CHANGELOG. Sin commit.

### P-D151-2 — Fuzzy match Ludusavi por nombre
Fecha: 2026-05-18  ·  Ejecutor: Opus  ·  Estado: DONE

Cambios:
- Añadida `pub fn find_by_fuzzy_name(name: &str, threshold: f32) -> Option<&'static LudusaviEntry>`
  en `crates/hoard-manifest/src/ludusavi.rs`, junto a `find_by_steam_app_id`
  para mantener juntas las funciones de lookup públicas del catálogo.
  Slugifica `name` con la misma `slugify` del módulo, calcula Levenshtein
  normalizado (`distance / max(len_query, len_slug)`) contra cada entry
  y devuelve la de menor distancia siempre que sea `< threshold`. Tie-break:
  cuando dos entries empatan, gana la que tiene `steam_app_id.is_some()`.
- Helper interno `pub(crate) fn fuzzy_match_in<'a>(catalog: &'a [LudusaviEntry], name, threshold)`
  contiene la lógica real; la pública es un wrapper que pasa `catalog()`.
  Extraído para que los tests usen un slice mock y mantengan tie-break
  determinista sin depender del catálogo embebido de ~20k entries.
- Añadido `strsim = "0.11"` como workspace dep en el `Cargo.toml` raíz
  y propagado a `crates/hoard-manifest/Cargo.toml` con `{ workspace = true }`.
  No estaba antes.
- Integración en `detect_all`: dentro de `apply_steam_name_fallback`
  (`crates/hoard-agent/src/detection.rs:485`), el `continue` de cuando
  el slug exacto no aparece en `catalog_by_slug` se convierte en una rama
  que llama a `ludusavi::find_by_fuzzy_name(&app.name, FUZZY_NAME_THRESHOLD)`
  (constante nueva = 0.15 en línea 537, documentada con la justificación
  Civilization V vs VI). Si el fuzzy resuelve, se crea el `DetectedGame`
  con `Confidence::Low` y `source = SteamLibrary`, exactamente igual que
  el slug-fallback. Log `tracing::info!` separado para distinguir hits
  de slug vs fuzzy en la telemetría.
- El flag `via_fuzzy` se propaga sólo dentro del bucle local; no se
  expone en el shape del `DetectionReport` (el plan 1.5.1 no exige
  un nuevo campo, y P-DET-6 ya tiene el panel de diagnóstico).

Archivos tocados:
- `Cargo.toml` — `strsim = "0.11"` en `[workspace.dependencies]`.
- `crates/hoard-manifest/Cargo.toml` — `strsim = { workspace = true }`.
- `crates/hoard-manifest/src/ludusavi.rs` — `find_by_fuzzy_name` +
  `fuzzy_match_in` + doc-comments + 4 tests unitarios.
- `crates/hoard-agent/src/detection.rs` — extensión de
  `apply_steam_name_fallback` con la rama fuzzy y constante
  `FUZZY_NAME_THRESHOLD` documentada.
- `docs/plans/1.5.1-log.md` — esta entrada + tabla.

Tests añadidos (todos pasan):
- `ludusavi::tests::fuzzy_matches_minor_typo` — "stardew vally" matchea
  "stardew-valley" en un slice mock.
- `ludusavi::tests::fuzzy_rejects_distant_names` — "destiny" no colapsa
  sobre "civilization-v"; "civilization" sí matchea (verifica que el
  threshold permite slug exacto-ish y rechaza distancia alta).
- `ludusavi::tests::fuzzy_prefers_steam_id` — "aac" equidistante a "aaa"
  (sin appid, primero en orden) y "aab" (con appid 42); el tie-break
  por `steam_app_id.is_some()` debe sustituir al no-appid → gana "aab".
- `ludusavi::tests::fuzzy_returns_none_below_threshold` — "minecraft"
  vs "portal-2" da distancia ≈ 1.0 > 0.15 ⇒ `None`.

Notas / decisiones de ejecución:
- **No se añadió `find_by_slug` pública**, aunque el prompt la cita.
  La razón: el flow ya existente en `apply_steam_name_fallback` usa
  un `HashMap<&str, &LudusaviEntry>` indexado sobre `catalog` (línea 468),
  más eficiente que un O(N) por app cuando se está iterando steam_apps.
  El fuzzy se añade como rama del `else` del lookup en ese hashmap, lo
  que conserva exactamente la semántica "appid None + slug None ⇒ fuzzy"
  del prompt sin duplicar pasadas sobre el catálogo.
- **Helper `fuzzy_match_in` `pub(crate)`** — necesario para que los
  tests construyan un catálogo determinista. Sin esto, `fuzzy_prefers_steam_id`
  depende de que dos entries empaten exactamente en el catálogo real, lo
  cual es frágil ante refresh del manifest.
- **`<` estricto en el threshold** — `distance < threshold` (no `≤`).
  Así con threshold 0.15 una distancia exacta de 0.15 ya no matchea;
  consistente con la cita del plan ("`distance / max(len_a, len_b) < 0.15`").
- **Tie-break implementado con `f32::EPSILON`** — comparar floats con
  `==` no garantiza el resultado esperado para divisiones donde el
  cociente cae en valores no representables; usar `(a - b).abs() < EPSILON`
  para considerar "iguales" distancias normalizadas idénticas en lógica.
- **Confidence::Low** — coincide con la del fallback por slug exacto.
  El razonamiento: el slug exacto ya es ambiguo (dos juegos no
  relacionados pueden compartir un slug); fuzzy es **al menos** tan
  débil. Tratar ambos como Low evita una taxonomía nueva de confidence
  para una distinción que el usuario no necesita.
- `cargo check --workspace` limpio; `cargo test --workspace` todo verde
  (incluidos los 4 nuevos + los 7 que añadió P-D151-1 + el resto).
- No se tocó el bloque del walker (P-D151-1), `Library.svelte`,
  `delete_save_completely`, versión, ni CHANGELOG. Sin commit.
