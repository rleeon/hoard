# 1.6.0 — Hoard Cloud (SaaS opcional)

> Séptimo ciclo. Convierte Hoard en un SaaS opt-in ("Hoard Cloud") con
> login social, planes de pago y storage gestionado, **sin romper
> self-hosted**. El binario `hoard-server` actual sigue siendo
> ciudadano de primera clase. Cloud es feature flag.
>
> Brief completo en
> [`docs/cloud/CLOUD-HANDOFF.md`](../cloud/CLOUD-HANDOFF.md).
> ADR formal en
> [`docs/decisions/0015-hoard-cloud-saas.md`](../decisions/0015-hoard-cloud-saas.md).
>
> Plan único fuente de verdad. Log vivo en
> [`1.6-cloud-log.md`](1.6-cloud-log.md).

---

## Stack decidido

| Componente              | Elección                       |
| ----------------------- | ------------------------------ |
| Auth + identidad        | Supabase Auth (OAuth + email)  |
| DB metadatos            | Postgres (Supabase managed)    |
| Storage snapshots       | Cloudflare R2 (S3-compatible)  |
| App backend             | Fly.io (`hoard-server-cloud`)  |
| Pagos                   | Lemon Squeezy (MoR)            |
| CDN + DNS               | Cloudflare                     |
| Email transaccional     | Resend                         |
| Errores                 | Sentry (opt-in vía prefs)      |
| Landing                 | Astro static + Vercel/Netlify  |

Dominio confirmado por el user: **hoard.services**.

Self-hosted sigue con SQLite + bearer tokens. El cliente desktop
soporta los dos modos (cloud o servidor propio) elegibles en
onboarding.

## Fases (P-CLD-*)

Cada fase = commit atómico con mensaje `cloud: <qué>`. Verificación
mínima antes de commitear: `cargo check --workspace` y
`pnpm --dir crates/hoard-desktop/ui check` verdes.

### P-CLD-0 — Setup cuentas y secretos (humano, no Claude)

**Bloquea las fases que requieren credenciales reales.** Claude
documenta el checklist; el user ejecuta:

- [ ] Cuenta **Supabase** + proyecto `hoard-cloud-prod` (region
      eu-central). Apunta `SUPABASE_URL`,
      `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`,
      `SUPABASE_JWKS_URL`, `SUPABASE_DB_URL`.
- [ ] Cuenta **Cloudflare** + dominio `hoard.services` + buckets R2
      `hoard-snapshots-prod` y `-staging`. Anota `R2_ACCOUNT_ID`,
      `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ENDPOINT`,
      `R2_BUCKET`.
- [ ] Cuenta **Lemon Squeezy** + store + 5 productos (Free,
      Pro mes/año, Pro+ mes/año). Apunta variant IDs,
      `LEMONSQUEEZY_API_KEY`, `LEMONSQUEEZY_WEBHOOK_SECRET`.
- [ ] Cuenta **Fly.io** + `fly apps create hoard-server-cloud`.
      Apunta `FLY_API_TOKEN`.
- [ ] Cuenta **Resend** + `RESEND_API_KEY`.
- [ ] Cuenta **Sentry** + project Rust + project JS. Apunta
      `SENTRY_DSN_RUST`, `SENTRY_DSN_JS`.

### P-CLD-1 — ADR + plan + branding · `done` (este commit)

- ADR `0015-hoard-cloud-saas.md` con resumen del handoff.
- Plan `1.6-cloud.md` (este archivo).
- Reorganización: 1.6.0 era CAS storage → ahora es Hoard Cloud. CAS
  se mueve a 1.7.0. Resumen en `CLAUDE.md` actualizado al cerrar
  cycle.

### P-CLD-2 — Postgres migrations + DB backend runtime

- Mantén `migrations/sqlite/*.sql` (renombra el dir actual) ó deja
  el actual y crea `migrations/postgres/*.sql` en paralelo.
- Migraciones Postgres: `profiles`, `subscriptions`, `devices`,
  `saves`, `save_versions`, `sync_log`, `audit_log`. RLS por
  `user_id`.
- `config.database.backend = "sqlite" | "postgres"`. Pool
  abstracto (`enum DbPool { Sqlite(SqlitePool), Postgres(PgPool) }`).
- Cualquier consulta nueva probada en ambos backends.
- **No tocar** las consultas existentes (siguen contra SQLite).

### P-CLD-3 — Trait `SnapshotStore` + R2 store

- Extraer la lógica `fs::rename` actual a `FsStore` (impl trait).
- Implementar `R2Store` con `aws-sdk-s3` apuntando al endpoint R2.
- Métodos: `put_object`, `get_object`, `delete_object`, `head`,
  `presign_put`, `presign_get`.
- Env: `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`,
  `R2_SECRET_ACCESS_KEY`.

### P-CLD-4 — Auth Supabase + JWT middleware

- Crate `jsonwebtoken`. Cargar JWKS al boot, cachear con
  refresh de 1 h.
- Middleware Axum: extrae `Authorization: Bearer <jwt>`, valida
  firma+exp contra JWKS, inyecta `CloudUser { user_id, email }` en
  extensions.
- Endpoint `POST /v1/profiles/sync` que crea la fila en `profiles`
  si no existe (idempotente).
- Stub: env `SUPABASE_JWKS_URL`.

### P-CLD-5 — Endpoints cloud nuevos

- `POST /v1/cloud/saves` — upload multipart (cliente sube vía
  presigned PUT a R2; servidor valida y registra).
- `GET /v1/cloud/saves/:id/download` — devuelve presigned R2 URL.
- `GET /v1/cloud/sync` — manifest de versiones del user.
- `GET /v1/me` — perfil + plan + uso actual.
- `POST /v1/me/export` — lanza job de export, devuelve job_id.
- `DELETE /v1/me` — soft-delete cuenta, 30 días de gracia.
- `POST /v1/webhooks/lemonsqueezy` — verify HMAC, actualiza
  `subscriptions`.

### P-CLD-6 — Quota enforcement

- Middleware: lee plan + `storage_bytes` antes de aceptar uploads.
- Si `requested + used > limit`, devuelve **402 Payment Required**
  con JSON `{error, plan, used_bytes, limit_bytes, upgrade_url}`.
- Limits hardcoded en `cloud::quota::PlanLimits`.

### P-CLD-7 — Deploy: Dockerfile + fly.toml

- Multi-stage: `rust:1.81-slim` builder → `gcr.io/distroless/cc`
  runner.
- Build flag `--features cloud`.
- `fly.toml`: app `hoard-server-cloud`, region `cdg`, autoscaling
  1-3 máquinas, healthcheck `GET /v1/health`.
- `.env.example` con todos los placeholders.

### P-CLD-8 — Cliente: login flow + tauri-plugin-deep-link

- `tauri-plugin-deep-link` registra `hoard://`.
- `tauri.conf.json` declara el scheme.
- Handler en `lib.rs`: parsea `hoard://callback?token=...&refresh=...`,
  guarda en keyring, emite evento `cloud://logged-in`.
- Comandos Tauri `cloud_*`:
  `cloud_start_login`, `cloud_complete_login`, `cloud_logout`,
  `cloud_refresh_account`, `cloud_open_billing_portal`,
  `cloud_open_upgrade_url`, `cloud_export_all`,
  `cloud_delete_account`.

### P-CLD-9 — UI `/account` + sidebar chip

- Ruta `/account` (Svelte) con avatar, plan actual, barra de uso,
  dispositivos, botones (mejorar plan, gestionar suscripción,
  exportar, borrar).
- Modal `UpgradePlanModal.svelte` con 3 columnas y toggle
  mensual/anual.
- Chip de cuenta al pie de la sidebar.
- Settings: nueva sección **Cuenta** con resumen + enlace.
- i18n keys nuevas en los 8 locales (en/es/de/fr/it/ja/pt/zh).

### P-CLD-10 — Tests + verificación final

- Unit tests con mocks (sin red): JWT validation, R2 client,
  quota middleware, webhook signature.
- Smoke test i18n (paridad de claves entre locales).
- `cargo check --workspace --features cloud` verde.
- `cargo check --workspace` (sin features) verde.
- `pnpm --dir crates/hoard-desktop/ui check` verde.

### P-CLD-11 — Landing web (`hoard-web`, repo aparte)

- Astro static, deploy Vercel/Netlify free.
- Páginas: home, precios, privacy, terms, contact.
- Checkout = links directos a Lemon Squeezy.
- Dominio: `hoard.services` → landing; `api.hoard.services` →
  Fly.io.

### P-CLD-12 — Observabilidad + cron

- Sentry SDK server + cliente (opt-in via `prefs.anonymous_telemetry`).
- `/metrics` (Prometheus) protegido por basic-auth.
- Cron diario (Fly machines `--cron`): recompute quota, downgrade
  expirados, sweep snapshots > retención, cleanup exports >7 días.

### P-CLD-Z — Release 1.6.0

- Bump versión 1.5.5 → 1.6.0 en `Cargo.toml`, `tauri.conf.json`,
  `package.json`, fallback en `App.svelte`.
- Block `## [1.6.0]` en `CHANGELOG.md`.
- README sección Cloud.
- Anuncio.

## Definition of done

1. Un user nuevo completa onboarding cloud, paga Pro y sube su
   primer save en < 5 min.
2. `pnpm i18n:check` sin diffs entre locales.
3. `cargo test --workspace --all-features` sin failures.
4. Self-hosted users existentes corren `hoard-server` sin
   feature flag y todo sigue funcionando (regression test).
5. Export-all produce un ZIP importable por `hoard-admin import`.
6. CHANGELOG con block `## [1.6.0]`.
7. ADR 0015 publicado, plan con todos los prompts `done`.
