### 2026-05-20 — P-D154-3 (Auto-restore diff no destructivo)

Bug: hasta 1.5.3 `crates/hoard-agent/src/agent.rs` solo dispara
auto-restore si `is_path_empty_or_missing(&local_path)` era true. Con
una carpeta poblada — aunque al snapshot remoto le falten archivos —
el agent no descargaba nada. El user pidió reconciliación: si el
snapshot remoto contiene archivos que faltan en local, traerlos. Si
un archivo está en ambos lados con bytes distintos, **gana local**
(no se toca; el watcher lo subirá luego).

Plan §4.2 nombró el helper renombrado `local_needs_restore`. La
implementación final se desvía levemente: el helper
`is_path_empty_or_missing` permanece como utilidad interna porque
`run_backup_with_retry` (skip-empty pre-check) sigue necesitándolo
sin contexto del snapshot. Lo que cambia es la lógica del decisor:
ya no es un gate previo al auto-restore — ahora `run_auto_restore`
siempre intenta el flujo (descargar → diff → copia) y la función
`restore_files_into` decide por archivo. Si nada falta, retorna
`restored == 0` y no emite evento.

#### Funciones añadidas / modificadas

- `crates/hoard-agent/src/agent.rs`:
  - **Nuevo** `restore_files_into(target: &Path, source: &Path) ->
    Result<RestoreStats>` (alrededor de la línea 770 tras los cambios)
    — walka recursivamente `source`, copia archivos faltantes en
    `target`, skipa conflictos preservando bytes locales, devuelve
    stats. Testeable sin red.
  - **Nuevo** `RestoreStats { restored, skipped, conflicts,
    bytes_restored }` (pub(crate) para los tests).
  - **Nuevo** helper privado `files_have_equal_bytes(a, b)` — compara
    tamaño primero y luego contenido completo, sin nuevas deps.
  - **Nuevo** `staging_dir_for(save_id)` — genera path único en
    `std::env::temp_dir()` con save_id sanitizado, counter atómico y
    PID. No usa `tempfile` en prod (cfg dev-only).
  - **Nuevo** `cleanup_staging(staging)` — borra el tempdir
    best-effort y solo loggea si falla.
  - **Reescrito** `run_auto_restore`:
    1. Resuelve `latest_version_num` (igual que antes).
    2. Crea staging dir único.
    3. Llama `download_snapshot(..., force=false)` contra el staging
       (vacío, así el `force=false` pasa).
    4. Llama `restore_files_into(local_path, staging)`.
    5. `cleanup_staging`.
    6. Devuelve `AutoRestoreOutcome { version_num, files_restored,
       files_conflicts, bytes_extracted }`.
  - **Reescrito** `AutoRestoreOutcome` para incluir `files_conflicts`
    y separar `files_restored` del antiguo `files_extracted`.
  - **Modificado** `spawn_auto_restore` (líneas ~599-680):
    - `restored > 0` → `tracing::info!("auto-restore diff: restored N
      files, M conflicts skipped (local wins)")` + emite
      `SaveAutoRestored` + `RearmWatcher`.
    - `restored == 0 && conflicts > 0` → `tracing::debug!` (silencio
      a nivel UI; no spam).
    - `restored == 0 && conflicts == 0` → silencio total.
    - Error → emite `SaveAutoRestoreFailed` (sin cambios).
  - **Modificado** `handle_add` (línea ~549): el gate
    `is_path_empty_or_missing` desaparece. Si `config.auto_restore`,
    siempre se llama `spawn_auto_restore`. La función de diff filtra.
  - **Modificado** `sweep_for_auto_restore` (línea ~671): el filtro
    `is_path_empty_or_missing` se quita. Sigue respetando el cooldown
    de 60 s (`AUTO_RESTORE_COOLDOWN_SECS`) y el flag `restoring`.
    Logging baja a debug porque ya no es "restaurando carpeta vacía"
    sino "diff por si acaso".
  - **Conservado** `is_path_empty_or_missing` (líneas ~576-587):
    `run_backup_with_retry` lo usa para no subir snapshots vacíos. No
    se renombra para mantener el cable simple.

#### Flujo nuevo (paso a paso)

1. Boot agent o `automatic-tick` o flip a `auto_restore=true`.
2. `handle_add` / `sweep_for_auto_restore` marca `slot.restoring = true`
   y `next_auto_restore_at = now + 60s`, luego spawn task.
3. Task llama `run_auto_restore`:
   - `api.get_save(save_id)` → si no hay `latest_version_num`,
     devuelve `Ok(None)` (server vacío). Sin evento, sin error.
   - `staging_dir_for(save_id)` → ruta única en `/tmp`.
   - `tokio::fs::create_dir_all(staging)`.
   - `download_snapshot(api, save_id, version, &staging,
     force=false)` → descarga + extrae el tarball al staging.
   - `restore_files_into(&save.local_path, &staging)`:
     - Walka el staging con un stack manual (sin recursion async).
     - Por cada archivo `rel`:
       - `target/rel` no existe → `create_dir_all(parent)` +
         `tokio::fs::copy`. `restored++`, `bytes_restored += copied`.
       - `target/rel` existe y bytes iguales → `skipped++`.
       - `target/rel` existe y bytes distintos → `conflicts++`,
         `tracing::debug!` "skipping conflict, local wins". Local
         intacto.
   - `cleanup_staging` (best-effort).
4. Task evalúa stats y loggea/emite:
   - `restored > 0` → log info + `SaveAutoRestored` + `RearmWatcher`.
   - `conflicts > 0 && restored == 0` → log debug, silencio UI.
   - Todo igual → silencio total.
5. `AutoRestoreFinished(save_id)` limpia `slot.restoring`.
6. Si el task falla en cualquier paso anterior, emite
   `SaveAutoRestoreFailed` (igual que antes).

#### "Local gana" en conflicto — justificación

Cuando `target/rel` existe localmente pero con bytes distintos al
snapshot remoto, **siempre** se preserva el local. Razón: el
auto-restore corre en background sin confirmación del user; si
sobreescribiéramos local por remoto, perderíamos trabajo en curso
del user (un save reciente que aún no ha subido el watcher). La
asimetría es deliberada — el camino "restaurar snapshot remoto
sobre local" sigue existiendo, pero solo vía el botón explícito
"Restaurar snapshot" de History/Dashboard, no por el modo
automático.

Consecuencia: el agent nunca destruye datos locales. Si el user
quiere forzar una restauración completa después de un crash, va
manualmente a History → restore.

#### Tests añadidos (`agent.rs` `mod tests`)

Inyectan un staging dir directamente sin red (la lógica de copia
quedó factorizada en `restore_files_into`):

1. `restore_files_into_copies_missing_files`: source = A, B,
   `nested/C`; target = solo A idéntico ⇒ `restored=2` (B + C),
   `skipped=1`, `conflicts=0`, `bytes_restored = |B| + |C|`. Asserta
   también que el contenido de A no cambió y que B + C aparecen con

2. `restore_files_into_preserves_local_on_conflict`: A en ambos con
   bytes distintos ⇒ `restored=0`, `conflicts=1`. Asserta que

3. `restore_files_into_silent_when_all_identical`: source y target

4. `restore_files_into_full_restore_when_target_empty`: target

Helper `write_file(path, contents)` añadido en `mod tests` para

#### Decisiones que se desviaron del plan

- **`is_path_empty_or_missing` conservado**: el plan §4.2 paso 1
  pedía renombrar a `local_needs_restore`. No se hizo porque el
  call site de `run_backup_with_retry` (skip-empty antes de subir)
  no necesita el snapshot remoto — solo necesita saber si la carpeta
  local está vacía. Renombrarlo a `local_needs_restore` hubiera
  forzado pasar un snapshot fake o cambiar la firma. Lo dejo como
  helper interno con su nombre original, y la "decisión de restore"
  vive en `restore_files_into`, no en un único bool.
- **No event nuevo `auto-restore-diff`**: el plan §5 mencionaba la
  posibilidad de añadir un evento Tauri nuevo si encajaba. Reusé
  `SaveAutoRestored` (que ya carga `files_extracted`/`bytes_extracted`)
  porque el frontend ya lo escucha y la semántica encaja: "se
  restauraron N archivos del snapshot". Los `conflicts` quedan en
  log debug porque no son user-visibles (no son un error).
- **`tempfile` no se añadió a prod deps**: regla "no introduzcas
  deps nuevas". Uso `std::env::temp_dir()` + counter atómico + PID
  para crear staging únicos. Cleanup vía `tokio::fs::remove_dir_all`.

### 2026-05-20 — P-D154-4 (Auto-backup stale en `automatic-tick`)

Bug reportado por el user: "noto que las cosas no se copian solas".
Causa raíz: el flujo `runAutomaticSetup` solo hacía
scan + add_game_to_tracking + boot_agent. Si el watcher se perdió un
evento (debounce muy largo, agent caído cuando el archivo cambió,
suspensión, app cerrada), el save local quedaba más nuevo que el
snapshot remoto y no se subía hasta el siguiente evento fs. Con la
cadencia del scheduler (6h default) este punto ciego puede durar
horas o días.

**Auditoría primero** — el plan pide reusar antes de añadir wrapper:

- Comando Tauri equivalente a `trigger_backup(save_id)`: **ya existe**
  como `backup_now(save_id)` en
  `crates/hoard-desktop/src/commands/agent.rs:117`. Está registrado en
  `invoke_handler!` y carga el `AgentHandle` desde `AppState`. Otros
  candidatos descartados: `history.rs` (snapshots/restore), `library.rs`
  (tracking), `automatic.rs` (toggle/scheduler). Único acertado:
  `agent.rs`.
- `AgentHandle::backup_now(save_id)`: **ya existe** en
  `crates/hoard-agent/src/agent.rs:245` — envía
  `AgentCommand::BackupNow(id)` al mpsc del agent loop. El loop
  (línea 431) lo procesa llamando `schedule_backup` con
  `Duration::ZERO` y `BackupReason::Manual`.
- Wrapper TS: **ya existe** como `export function backupNow(save_id:
  string): Promise<void>` en
  `crates/hoard-desktop/ui/src/lib/api/index.ts:339`.
- **Reúso completo**, no se añade nuevo comando ni wrapper.

Dedup interno del agent: `schedule_backup` aborta el `pending` task
previo del slot antes de agendar el nuevo
(`crates/hoard-agent/src/agent.rs:1017-1019`: `if let Some(p) =
slot.pending.take() { p.abort(); }`). Eso significa que invocar
`backup_now` repetidamente sobre el mismo save no genera N backups
concurrentes — la versión vieja se cancela y solo corre la última.
No es un mutex estricto (un backup en vuelo no se aborta si ya
empezó la subida en `run_backup_with_retry`), pero sí cubre el caso
de spam por barrido del tick. Suficiente para no hacer scope-creep.

Cambios en `crates/hoard-desktop/ui/src/lib/stores/automatic.ts`:

- Tipo `AutomaticPhase` (L32-37): añadido `| { kind: "syncing" }` para
  cubrir el nuevo paso.
- Nuevo helper `runBackupStaleSweep(saves)` (L60-92): pone
  `automaticState` en `syncing`, itera la lista de `TrackedSave`,
  llama `api.backupNow(save.save_id)` con try/catch individual y
  `console.warn` con el `save_id` para no abortar el barrido si un
  save falla. Devuelve el contador. Comentario in-line cita el plan y
  el dedup interno del agent.
- `runAutomaticSetup`:
  - Rama "nothing to track" (L113-119): tras el `bootAgent` añade un
    barrido sobre `tracked` (la lista que ya teníamos cargada para
    intersectar slugs). El toast `nothing_new` y el reset a `idle`
    quedan después del barrido.
  - Rama normal (L152-156): tras `bootAgent` refresca la lista
    llamando `api.listTrackedSaves()` (porque los `addGameToTracking`
    de este tick acaban de incorporar saves nuevos que merece la pena
    subir), con fallback al `tracked` original si falla. Luego barre.
