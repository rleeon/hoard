> detección descrito en [`detection.md`](detection.md), no el CAS storage

## 0. Contexto y diagnóstico

La 1.0 cerró la promesa de producto (cliente nativo + servidor self-hosted
+ catálogo Ludusavi). La 1.3.x ha pulido la UX del cliente: detección,
tracking, brand emerald y un updater in-app. El armazón está sólido, pero
quedan seis zonas blandas:

1. **Watcher del agente silenciosamente roto** (P0). El usuario reporta
   que con un save tracked y el juego abierto guardando in-game,
   hoard-desktop nunca dispara backups y la pill del Dashboard se queda
   en "Inactivo" para siempre. Causa: `crates/hoard-agent/src/agent.rs`
   declara el fs watcher como `Option<Debouncer>` en
   `SaveSlot._watcher` y sólo lo construye al recibir `GameStarted`
   (comentario explícito "the fs watcher is **not** started here" cerca
   de la línea 314). `GameStarted` viene de `process_poll`, que matchea
   el proceso vivo contra `WatchedSave.processes` (lista del manifest
   Ludusavi, frecuentemente vacía) o contra el prefijo de
   `steam_install_dir`. Si ninguno pega — manifest sin processes, juego
   no-Steam, o exe fuera del install_dir esperado — nada dispara, el
   watcher no se arma, no se emiten eventos al UI y el autobackup
   desaparece sin un solo log. Regresión del core value del cliente
   ("backup automático en background"); cualquier juego cuya entrada
   Ludusavi no traiga `processes` está hoy desprotegido.
2. **UX del cliente con bugs visibles**. Otros tres asuntos cosméticos
   acumulados:
   - El cache de detección vive sólo en `Mutex<Option<DetectionReport>>` en
     `AppState` (ver `crates/hoard-desktop/src/state.rs` y
     `crates/hoard-desktop/src/commands/library.rs:93`): al reiniciar la app
     se pierde y hay que re-escanear a mano cada vez.
   - El sidebar tiene etiquetas hardcoded en inglés
     (`crates/hoard-desktop/ui/src/App.svelte:100-103`) — "Library",
     "Dashboard", "History", "Settings" no pasan por `$_()` y se ven igual
     en cualquier locale.
   - La pill del Dashboard arranca siempre como "Inactivo"
     (`Dashboard.svelte:pillFor`) aunque el save ya tenga
     `last_version_num` en el servidor. Cosmético sobre #1: incluso con
     el watcher arreglado, en arranque en frío sigue sin haber
     `$activity` hasta el primer evento; el fallback a
     `last_version_num` evita el mensaje confuso mientras tanto.
3. **Cobertura de tests**. 17 archivos con `#[test]`, pero
   `tests/integration/` y `tests/fixtures/` están vacíos. Cero tests del
   UI Svelte. Cero tests end-to-end del flujo backup → restore contra un
   server real. La regresión típica (Stellaris, `track()` ambush,
   re-tracking 409, blank window por i18n) llega siempre en producción.
4. **Operabilidad del servidor**. `/v1/health` y nada más. Sin métricas,
   sin readiness probe, sin rate limit nativo, sin backup automatizado de
   SQLite, sin logs estructurados JSON. Cualquiera que corra Hoard
   "como un servicio" lo nota.
5. **Eficiencia de almacenamiento**. Cada snapshot es un `tar.zst`
   completo. Para saves grandes (Stellaris, Civ, Bannerlord) el cuota
   default de 100 GiB se llena en semanas. El plan original de la 0.3
   mencionaba chunking + dedup; nunca aterrizó.
6. **DX**. `guide0-3` sin extensión, sin `justfile`, sin `docs/dev.md`,
   sin pre-commit. El onboarding contributor es leer `CONTRIBUTING.md` y
   adivinar el resto.

Hay además dos pendientes de producto que arrastramos desde la 1.3.x:

- **Stellaris path-detection** (open item en `CLAUDE.md`).
- **Rename label** de un save (limitación documentada desde 0.2).

## 1. Objetivos no-negociables

- **1.4.x** es cosmética y deuda: cierra los pendientes de producto y
  estabiliza la base sin tocar API ni schema.
- **1.5.0** introduce capacidades nuevas con compromiso de
  compatibilidad: el cliente 1.4 sigue hablando con un server 1.5 sin
  cambios, y los snapshots 1.x viejos siguen siendo restaurables tras
  cualquier reorganización de storage.
- Toda mejora con riesgo arquitectural lleva ADR (`docs/decisions/`).
- CI verde (incluye los nuevos jobs) es prerrequisito de merge a `main`.

## 2. No-goals globales del ciclo 1.4 → 1.8

- Multi-tenant / registro público / billing.
- Web UI completa del servidor (admin sigue siendo CLI; un panel de
  diagnóstico read-only entra en 1.7 pero no es una UI de gestión).
- macOS Apple Silicon como runner de CI (sigue siendo build-only).
- Migración fuera de SQLite. ADR 0001 sigue vigente.
- Auto-update del server sin intervención del operador (ADR 0008).

Code-signing Windows/macOS estaba en no-goals de 1.5; vuelve a entrar
como objetivo en 1.8 cuando los certs estén disponibles (ver §3.1.8).

## 3. Roadmap por release

### 1.4.0 — limpieza, pendientes de producto

Patch+minor mezclados. Sin features grandes. El bug funcional del
watcher va primero (rompe el core value); el resto son UX visibles que
arruinan la primera impresión.

- **Watcher del agente siempre activo (P0)**: hoy el fs watcher es
  lazy y sólo arranca al recibir `GameStarted`, que depende de
  matching de proceso (manifest o `steam_install_dir`). Cuando ninguno
  pega, no hay eventos ni backups aunque el juego esté guardando.
  Cambio: construir el debouncer al hacer track (en `handle_add`), no
  al recibir `GameStarted`. El `process_poll` sigue informando al UI
  pero ya no gatea el fs watching. Telemetría obligatoria
  (`tracing::info!` en armado, evento fs, schedule, transición de
  proceso) y comando de diagnóstico `agent_status`. Detalle y
  verificación en P1.4.0-0.
- **Persistir el cache de detección y re-escanear solo**: hoy
  `DetectionCache` vive en memoria. Persistir el `DetectionReport` en
  el state file del agente (junto a `CliState`) o en un archivo aparte
  (`detection.json`) con `last_scanned_at`. Al arrancar, hidratar de
  disco para que `cached_detection` devuelva algo y la página Library
  pinte instantáneamente. Política: si pasaron >24h desde
  `last_scanned_at`, disparar un scan en background y refrescar al
  acabar. Botón "Re-escanear ahora" en la Library page (ya hay sitio en
  el header) para forzarlo a mano.
- **Traducir el sidebar**: `App.svelte:100-103` tiene los labels
  hardcoded. Reemplazar por `$_("nav.library")`, `$_("nav.dashboard")`,
  `$_("nav.history")`, `$_("nav.settings")`, y añadir las 4 claves a
  los 8 locales (`en/es/de/fr/it/ja/pt/zh.json`).
- **Pill del Dashboard coherente con el estado real**: `pillFor` debe
  consultar primero `$activity[saveId]`; si no hay activity, mirar
  `tracked.last_version_num`. Cuando es `Some(n)`, pinta
  "vN guardado" con `Check` icon y verde. Cuando es `None`, pinta
  "Sin copia aún" con `CircleDot` y zinc. El estado "Inactivo" se
  borra: nunca fue informativo, sólo confuso.
- **Stellaris path-detection**: el auto-detector cree que el path
  absoluto encontrado es el save dir y suprime la alerta amber. Otros
  juegos sí la muestran. Probable foco: `hoard-detect` o la
  alert-suppression de `library.rs`.
- **Rename label**: acción en la History/Library para renombrar el
  `label` de un save existente. Server-side: nuevo endpoint
  `PATCH /v1/saves/{id} { label }` que respeta `UNIQUE(user_id,
  game_slug, label)`. Cliente: modal de confirmación, persistir local.
- **Updater periódico**: el chequeo se hace al arranque y al abrir
  Settings. Añadir un timer cada 6h con backoff exponencial al fallo
  (cap 24h) para que un usuario que deja la app abierta días vea el
  nag. Sin cambios al endpoint, no consume más de 8 req/día contra
  GitHub.
- **`guide0-3` → `docs/plans/0.3.md`** y este archivo a
  `docs/plans/1.5.md`. Mantener un symlink en raíz solo si Claude se
  queja al leerlo.

### 1.4.1 — DX

Paralelizable con 1.4.0. Sin impacto en usuarios.

- **`justfile` en la raíz** con: `dev` (server local + migrate +
  usuario seed), `check` (cargo check + pnpm check), `test` (test
  workspace + ui), `release` (verifica las 4 versiones, hace el bump
  y abre el CHANGELOG en `$EDITOR`).
- **`docs/dev.md`**: primera vez en el repo. Env vars (`SQLX_OFFLINE`,
  `DATABASE_URL`), pnpm/cargo prereqs, cómo correr el agente
  apuntando a un server local, dónde mirar los logs.
- **`.githooks/pre-commit`** opcional: `cargo fmt --check` y `pnpm
  check` rápidos. Activado con `git config core.hooksPath .githooks`.

### 1.4.2 — calidad de CI (sin features visibles)

- **Matrix de SO** en `build-test`: `ubuntu-latest`, `windows-latest`,
  `macos-14`. Sólo `cargo check --workspace` en Win/macOS (los tests
  de servidor exigen herramientas Linux). Garantiza que `hoard-cli` y
  `hoard-agent` siguen compilando en las plataformas que importa.
- **`cargo sqlx prepare --check`** como step propio. Si el cache de
  `.sqlx/` se queda atrás, falla aquí en vez de fallar misteriosamente
  en clippy.
- **`cargo deny`**: ejecuta `cargo deny check advisories bans licenses`.
  Bloquea CVEs y deps con licencia incompatible (GPL ≠ AGPL al
  servidor está bien; un dep MPL en `hoard-core` no).
- **`cargo machete`**: detecta deps no usadas. Soft fail al inicio
  (warning), hard fail tras un sprint de limpieza.
- **Lint i18n**: script Node corto (`scripts/check-i18n.mjs`) que
  carga `en.json` como base y verifica que los 7 idiomas restantes
  tienen exactamente las mismas claves. Falla si hay huérfanas o
  faltantes. Listed en CI.

### 1.5.0 — operabilidad y eficiencia

La release "real" del ciclo. Tres bloques.

#### 3A. Tests end-to-end

- **Crate nuevo `hoard-e2e`** (test-only, no publicado): levanta un
  `hoard-server` en `tokio::spawn`, crea usuario+token, ejecuta
  backup→restore en un tmpdir, valida hashes. Vive en `tests/` de
  workspace para que `cargo test --workspace` lo arrastre. Reusa
  `ApiClient` de `hoard-agent`.
- **Tests UI con Vitest** en `crates/hoard-desktop/ui/`. Cubre los
  stores (`updates.ts`, `magic.ts`, `toasts.ts`) y el parsing de
  versiones del updater. Sin Playwright todavía; el costo de mantener
  E2E browser es alto y la regresión de UI puro la cubre `svelte-check`.
- Añadir `pnpm test` al CI step `build-test`.

#### 3B. Operabilidad del servidor

- **`/metrics`** Prometheus en el server. Métricas clave:
  `hoard_snapshots_total{outcome}`, `hoard_snapshot_bytes_total`,
  `hoard_request_duration_seconds{route}`,
  `hoard_storage_used_bytes{user_id}`. Crate: `metrics` + 
  `metrics-exporter-prometheus`. Detrás del bearer-token igual que
  el resto.
- **`/readyz`** separado de `/v1/health`. `/v1/health` ya retorna 200
  apenas el binario está vivo (lo necesita el updater); `/readyz`
  requiere DB accesible y `data_dir` escribible. Misma route module.
- **Rate limit por token** in-process: `tower-governor` o equivalente,
  configurable en `config.toml` (`[rate_limit] per_token = "120/min"`).
  Default off para no romper a quien ya corra con un reverse proxy
  haciendo el rate limit.
- **Logs JSON** opt-in: `--log-format=json` en
  `hoard-server`/`hoard-cli`. `tracing-subscriber` ya tiene el feature
  `json`. Default sigue siendo human-readable para no romper a quien
  scrolle `journalctl`.
- **Backup automático SQLite**: tarea `cleanup`-style que cada 24h
  hace `VACUUM INTO backups/hoard-YYYY-MM-DD.db` y purga los más
  viejos de N días (configurable, default 7). El usuario sigue
  necesitando llevarse esos archivos fuera; el server no sabe de S3.
- **`hoard-server upgrade --restart`**: opt-in, con prompt. Tras
  `fs::rename` del binario, hace `systemctl restart hoard-server` si
  detecta systemd. Sin systemd, falla con instrucciones. Si hay un
  sync en curso (cualquier request multipart con estado abierto en
  memoria), espera hasta 30s antes de reiniciar; al timeout cancela
  con error claro.

#### 3C. Storage: chunking + dedup

El más invasivo. ADR nuevo (`0009-content-addressed-storage.md`)
**antes** de empezar.

- Cada archivo del save se trocea en chunks (FastCDC, 4–8 MiB target,
  Rabin fingerprint).
- Cada chunk se almacena como `data/blobs/<hash[0:2]>/<hash>.zst`,
  content-addressed, escrito atómicamente vía `tmp/`.
- Un snapshot pasa a ser un manifest JSON con `[path, mode,
  chunks[]]`. El manifest es lo único nuevo que se guarda por commit.
- Restore reensambla en streaming descargando chunks únicos. Verify
  SHA256 final como hoy.
- **Compatibilidad**: snapshots 1.x existentes siguen sirviéndose
  desde su `tar.zst` original. El server detecta el formato por el
  campo `snapshot_format` ('tarzst' | 'cas') en la fila de la DB. Los
  snapshots nuevos van a 'cas'; los viejos nunca se reescriben.
- Métrica clave: `hoard_dedup_ratio` (bytes lógicos / bytes físicos).
- Quota cuenta bytes lógicos referenciados por el usuario (no físicos
  globales). Una garbage collection diaria libera blobs sin
  referencias.

### 1.6.0 — pulido del cliente

Sin features grandes nuevas: rematar lo que el usuario ve y siente
todos los días. Cero cambios al protocolo HTTP salvo el endpoint
`/v1/storage` (nuevo, opcional, retrocompatible: si el server lo
ignora el cliente sigue mostrando la cuota como hasta ahora).

- **Almacenamiento real en modo self-hosted**: `QuotaBar.svelte` hoy
  muestra `storage_quota_bytes` aunque el server sea local. La cuota
  no significa nada cuando tú mismo escribes el `config.toml`. Server:
  nuevo endpoint `GET /v1/storage` que devuelve `{ data_dir_total_bytes,
  data_dir_free_bytes, data_dir_used_bytes }` haciendo `statvfs` (o
  equivalente en Windows) sobre `data_dir`. Sólo accesible con token
  admin. Cliente: cuando `is_local_server` es true, `QuotaBar` consulta
  el endpoint y pinta "X usado / Y libre en disco" en lugar de la
  cuota. Fallback a la vista actual si el endpoint no existe (server
  antiguo) o el usuario no es admin.
- **Notificaciones del sistema** (Tauri `notification` plugin): toast
  nativo cuando un backup termina, falla o cuando el agente detecta
  un save no protegido tras varias modificaciones. Opt-in en Settings
  (default off el primer launch tras el upgrade; se pregunta una vez).
  Respeta el "modo silencio" mientras el juego está corriendo
  fullscreen.
- **Búsqueda + filtros en History**: el History page muestra una
  lista plana de snapshots ordenada por fecha. Añadir un input de
  búsqueda (por game, por label, por fecha en formato libre) y filtros
  rápidos (sólo último mes, sólo este game, sólo restaurados).
  Server-side sigue sirviendo `GET /v1/snapshots?since=&game=&label=`;
  añadir esos query params si no existen (revisar
  `crates/hoard-server/src/routes/snapshots.rs`).
- **Magic con feedback granular**: hoy `runMagicSetup` (ver
  `crates/hoard-desktop/ui/src/lib/stores/magic.ts`) reporta sólo
  fases. Cambiar a un stream de eventos `magic://progress` con el
  game actual, los que fallaron y por qué, los que se omitieron por
  ya estar trackeados. La sidebar pasa de "Tracking 3/12…" a un
  collapsible que se queda visible 10s al acabar con el resumen
  completo. Permite reintentar los fallidos uno a uno.
- **Pausa global**: master switch en Settings que detiene todo
  watcher y backup hasta despausar. Distinto del pause por save (que
  ya existe). Útil cuando el usuario está editando archivos del save
  a mano. Persiste en `CliState`. En la sidebar, indicador visible
  (un punto rojo o una banda) que recuerda que el agente está parado.
- **Diff entre versiones de un snapshot**: en la History, al pinchar
  un snapshot, mostrar archivos añadidos, modificados y borrados
  respecto al snapshot anterior del mismo save. Para CAS es trivial
  (comparar manifests); para snapshots `tar.zst` antiguos, requiere
  descargar ambos y diff de listing. Limitar a "mostrar sólo nombres,
  no contenido"; bytes-level diff queda para más adelante.
- **Tray menu con acciones rápidas**: hoy el tray icon abre la
  ventana y poco más. Añadir items: "Backup ahora (de todo)",
  "Abrir último backup", "Pausar / reanudar globalmente", "Salir".
  Tauri `tray::Menu` lo soporta nativo.

### 1.7.0 — robustez del servidor

Pensado para que un Hoard que lleva meses corriendo siga siendo
operable. Todo opt-in y backwards-compatible. No toca el protocolo
HTTP del cliente.

- **Verificación de integridad programada**: tarea en `cleanup.rs`
  que cada N días (config, default 30) recorre los blobs CAS,
  recalcula SHA256 de una muestra (configurable: por defecto 5% por
  pasada) y reporta blobs corruptos en un log dedicado
  (`integrity.log`) y como métrica
  `hoard_integrity_corrupt_blobs_total`. No borra ni "auto-repara":
  el operador decide. Para snapshots `tar.zst` legacy, verifica
  recalcular el hash del archivo entero ocasionalmente.
- **Retención por save**: hoy la retención (días para purgar trash,
  número máximo de snapshots) es global en `config.toml`. Añadir
  override por save: `PATCH /v1/saves/{id}` acepta
  `retention_days`/`retention_max_versions` opcionales. Migración SQL
  añade columnas nullable; un NULL hereda del global. UI: sección
  "Retención" en la modal de detalles de un save.
- **Audit log persistente**: tabla `audit_log` con
  `(id, ts, user_id, token_id, action, target_kind, target_id,
   ip, user_agent, status)`. Acciones registradas: login,
  snapshot_create, snapshot_delete, snapshot_restore, save_create,
  save_rename, save_delete, token_create, token_revoke. Endpoint
  `GET /v1/admin/audit?since=&user=&action=`. Rotación: tarea
  `cleanup.rs` purga >180 días (config). Si el log crece >100k
  filas se notifica al operador en logs.
- **Panel de diagnóstico HTML** (`/admin/status`): página estática
  servida por el server, autenticada por token admin via header o
  query param. Muestra: versión, uptime, disk free/used del
  `data_dir`, número de usuarios y saves, métricas básicas
  (snapshots últimas 24h, errores 5xx últimas 24h), últimos 50
  entries del audit log. Read-only. No es "Web UI"; es un dashboard.
- **GC observable**: `hoard-admin gc --dry-run` lista blobs sin
  referencias, agrupados por edad, y reporta cuánto se liberaría.
  Sin `--dry-run`, borra. La tarea automática diaria sigue
  ejecutándose pero ahora con un log estructurado del resultado.
- **Token scopes**: hoy los tokens son binarios (admin o no). Añadir
  scopes mínimos: `read`, `write`, `admin`, `metrics`. Migración SQL
  no-destructiva (NULL = admin si created_at < migración fecha, sino
  defaults a `read+write`). El `hoard-admin token create` gana `--scope`.
  Endpoint `/metrics` exige scope `metrics` o `admin`.

### 1.8.0 — plataformas y casos avanzados

La release más ambiciosa del ciclo. Riesgo alto en signing (depende
de certificados externos); si no llegan, se desacopla a 1.8.1.

- **Steam Deck mode**: detección Proton (`compatdata/<appid>/pfx/`),
  paths bajo `drive_c/users/steamuser/...`. Hoy `hoard-detect` asume
  paths nativos Linux. Añadir una rama Proton al sweep cuando se
  detecta `~/.steam/steam/steamapps/compatdata/`. ADR previo
  obligatorio (`0012-proton-detection.md`) describiendo el mapping y
  los edge cases (saves en `AppData/Roaming` vs `Documents` vs
  `LocalLow`).
- **Multi-user switching en cliente**: hoy el desktop guarda una
  sola credencial. Permitir N cuentas guardadas (puede ser el mismo
  server con tokens distintos, o servers distintos). Selector en el
  sidebar (avatar + dropdown). `Credentials::save` pasa a
  `Vec<Credentials>` con un `active_index`. Migración del archivo en
  disco: si encuentra el formato viejo, lo envuelve en una lista de
  uno al cargar y reescribe en el siguiente write.
- **Windows registry / AppData hooks**: Ludusavi lista entradas de
  registro y AppData para muchos juegos; hoy las ignoramos. Añadir
  soporte en `hoard-manifest` y `hoard-agent` para incluirlas en el
  snapshot (export del subárbol de registro como `.reg` + carpetas
  de AppData). Restore aplica con `reg import` y copia inversa.
  Sólo Windows; los snapshots con registro llevan un flag
  `has_registry` para que el cliente Linux/macOS no intente
  restaurarlos en un host equivocado.
- **Codesigning Windows + macOS**: ADR `0011-codesigning.md` con la
  decisión de proveedor (DigiCert/SSL.com para Windows EV,
  Apple Developer ID para macOS), coste anual y mecanismo de
  almacenamiento de claves en CI (GitHub OIDC + secrets manager
  external). Workflow `release-desktop.yml` gana steps de
  `signtool.exe` y `codesign`/`xcrun notarytool`. Si los certs no
  están disponibles en la fecha objetivo, la 1.8 sale sin signing y
  esto se mueve a 1.8.1.
- **Hooks pre/post backup**: scripts user-defined que el agente
  ejecuta antes y después de cada snapshot. Útil para saves que
  requieren preprocesado (descomprimir, dump de DB de un juego)
  o post-procesado (enviar a un canal de Discord cuando se hace un
  backup importante). Config en `CliState` por save:
  `pre_hook: Option<PathBuf>`, `post_hook: Option<PathBuf>`.
  Timeout por hook (default 30s). Stderr del hook va a un log
  visible en la UI.
- **Onboarding wizard mejorado**: hoy es paso a paso textual.
  Añadir 2–3 capturas de pantalla animadas (GIF o video corto sin
  audio) en cada paso. Recurso bundled en el `.deb`/`.msi`/`.dmg`.

## 4. Checklist por release

Antes de etiquetar `v1.X.Y`:

1. `cargo check --workspace` y `pnpm --dir crates/hoard-desktop/ui
   check` limpios.

## 6. Riesgos y mitigaciones

- **CAS introduce un GC**: si el GC borra un blob referenciado, el
  snapshot queda corrupto. Mitigación: GC sólo borra blobs cuya
  última referencia desapareció hace ≥ 24h, y un dry-run loggea
  cuánto liberaría antes de el primer run real.
- **Rate limit puede romper sync legítimo** de un usuario con
  centenares de saves. Default off y configurable; documentar el
  cálculo (saves * frecuencia / 60s).
- **Migración 0.x → CAS**: no la hay. Snapshots viejos se sirven
  con el path antiguo de por vida. Hace falta cero downtime.
- **CI matrix triplica el coste de minutos**: usa
  `Swatinem/rust-cache` agresivamente y limita Win/macOS a
  `cargo check`. Si el coste duele, mover macOS a "manual trigger"
  antes de release.
- **1.6 toca QuotaBar y el flujo del Magic button**: ambas
  superficies son visibles desde el primer minuto. Cambios sin
  screenshots en la PR son rechazados.
- **1.7 introduce un audit log persistente**: crece sin techo si no
  hay rotación. El plan obliga a retención configurable y a una
  tarea de purge en `cleanup.rs`.
- **1.8 codesigning depende de certs**: bloquea la release entera si
  no están firmados a tiempo. ADR 0011 marca la decisión de cuándo
  romper la promesa "instalable sin warning" — si los certs no llegan,
  la 1.8 sale sin signing pero documenta el estado.
