### 2026-05-19 — P-D153-1 (Error envelope estructurado + ErrorDialog)

Tipo `AppError { title, body, detail }` aterrizó como módulo nuevo
`crates/hoard-desktop/src/commands/error.rs` con `#[derive(Serialize)]`,
helpers `new` / `with_detail` / `plain` y `From<String>` /
`From<&str>` para retrocompat con `?` sobre cadenas crudas. Declarado
en `commands/mod.rs` como `pub mod error;` (sin `pub use` para evitar
warning de import no usado mientras los demás comandos siguen en
`Result<_, String>`).

- `apply_desktop_update` ahora devuelve `Result<ApplyOutcome,
  AppError>`. Cada rama de fallo construye un `AppError` específico:
  fallo de `fetch_gh_release` → `updates.error.unknown`; ausencia de
  asset compatible → `updates.error.no_installer` con detalle
  `v{ver} · Assets: a, b, c`; resolución de download dir y
  `create_dir_all` → `updates.error.download_failed`; `download_to`
  → `updates.error.download_failed`. La rama de `launch_installer`
  no falla a `Err` (cae a `Downloaded`), así que `launch_failed`
  queda reservado para futuros usos directos.

  AppError>`. Errores de spawn de `pkexec` o pkexec con exit no-cero
  → `updates.error.server_pkexec_failed` con stderr/stdout/exit
  status como detalle. La variante `#[cfg(not(target_os = "linux"))]`
  → `updates.error.server_unknown` con la frase "In-app server
  upgrade is only supported on Linux today…" como detalle.
- Helpers internos (`fetch_gh_release`, `download_to`,
  `launch_installer`, etc.) siguen retornando `Result<_, String>` —
  la conversión a `AppError` se hace en el último `?` del comando
  Tauri público, conforme al spec del prompt.

### 2026-05-19 — P-D153-4 (Modo Automático toggle + scheduler)

`Prefs` (`crates/hoard-agent/src/prefs.rs`) gana dos campos aditivos
con `#[serde(default)]`/`#[serde(default = "default_scan_interval_hours")]`
para no romper `prefs.json` pre-1.5.3:

- `automatic_mode: bool` (default `false`) — espejo persistido del
  toggle del sidebar.
- `automatic_scan_interval_hours: u32` (default `6`) — intervalo entre
  scans en background. Sin UI Settings por ahora; queda como campo
  serializado para que un slider futuro no requiera migración.
- `impl Default for Prefs` actualizado con ambos.
- Tres tests nuevos (`#[cfg(test)] mod tests`):
  `defaults_match_documented_values` (defaults completos incl. los
  campos viejos), `pre_153_json_deserialises_with_new_defaults`
  (JSON 1.5.2 sin las dos keys ⇒ defaults aplicados), y
  `round_trip_preserves_non_default_automatic_mode`
  (`automatic_mode = true` + `interval = 12` ⇒ round-trip estable).
  `cargo test -p hoard-agent prefs` reporta 3 pasados.

Scheduler singleton en
`crates/hoard-desktop/src/commands/automatic.rs`:

- `pub struct AutomaticScheduler { handle: Arc<Mutex<Option<JoinHandle<()>>>> }`
  registrada como `tauri::State` managed en `lib.rs::run`
  (`app.manage(AutomaticScheduler::default())`).
- `pub fn start(app: &AppHandle, interval_hours: u32)`: cancela el
  handle previo (`.abort()`), spawna `tokio::time::interval` con
  período `hours * 3600 s` (clamp `max(1)` para evitar tick infinito
  si llega un 0), consume el primer tick inmediato porque
  `interval()` dispara al instante, y en cada tick subsiguiente loguea
  `tracing::info!("automatic mode: scheduled scan starting")` y emite
  el evento Tauri `automatic-tick`. Comentario en el módulo explica
  por qué no se replica `runMagicSetup` completo en Rust: la pipeline
  (scan + track + boot agent) usa stores y toasts UI-side; tener dos
  implementaciones drift-eable es peor que cruzar el bridge una vez.
- `pub fn stop(app: &AppHandle)`: lock + take + abort si Some.
- `pub async fn restart_if_enabled(app: &AppHandle) -> Result<()>`:
  carga prefs, si `automatic_mode == true` arranca `start(...)` con
  el interval persistido. Llamado desde la closure `setup` de Tauri
  con `tauri::async_runtime::spawn` para rehidratar el scheduler
  tras un cierre/apertura sin requerir flip del toggle.

Comando Tauri `set_automatic_mode(enabled: bool)` en
`crates/hoard-desktop/src/commands/prefs.rs`:

- Devuelve `Result<Prefs, AppError>` (`AppError::plain(e.to_string())`
  en cada path de fallo de load/save, importado de
  `crate::commands::error::AppError`).
- Cascada `auto_restore`: si `enabled` y `prefs.auto_restore == false`,
  se sube a `true` y `auto_restore_changed = true`. Si `!enabled`, el
  campo queda intacto (independencia hacia abajo, conforme al plan).
- Tras `prefs.save(&path)`, si `auto_restore` cambió a `true` se
  replica la lógica de `save_prefs`: lock del `AppState.agent`,
  `AgentHandle::set_auto_restore(true).await`. Errores aquí son
  warnings — el cambio en disco ya está aplicado.
- Llama `automatic::start(&app, prefs.automatic_scan_interval_hours)`
  o `automatic::stop(&app)` según el flag.
- Registrado en `invoke_handler!` junto a `set_autostart` /
  `is_autostart_enabled`.

UI:

- `crates/hoard-desktop/ui/src/lib/stores/automatic.ts` reemplaza a
  `magic.ts` (eliminado). Mismo flujo `scan → track high-confidence →
  bootAgent` pero re-nombrado: `runAutomaticSetup`, `automaticState`,
  `AutomaticPhase`. Los toasts ahora se resuelven con i18n

- `crates/hoard-desktop/ui/src/lib/api/index.ts`: el tipo `Prefs`
  gana `automatic_mode: boolean` y `automatic_scan_interval_hours: number`
  (no había un `.d.ts` separado — el shape vive aquí, en el wrapper).
  Wrapper TS nuevo `setAutomaticMode(enabled)` que invoca
  `set_automatic_mode` y devuelve `Promise<Prefs>`, colocado junto a
  `savePrefs`.
- `crates/hoard-desktop/ui/src/lib/stores/prefs.ts`: el fallback de
  defaults en `hydratePrefs` añade ambos campos.
- `crates/hoard-desktop/ui/src/App.svelte`:
  - Imports: `runAutomaticSetup, automaticState, initAutomaticListener`

  - `onMount`: llama `initAutomaticListener()` antes del fetch de
